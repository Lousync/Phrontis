### 簇内共享的两个底层口径（先钉住，否则方案会跑偏）

1. **作用域是「前缀覆盖」，不是「文件集合」。** 真源 `electron/lib/kbStore/vaultScope.ts:23-30`：
   `norm === p || norm.startsWith(p + '/')`。勾一个目录 = 一条前缀，天然覆盖其下全部；读写同源（`electron/lib/aiAssistantScope.ts` 的 `canRead` / `canWrite` 都走它）。
2. **「空 scope」= 不设限，而不是「什么都没选」。** `electron/lib/aiAssistantScope.ts:17` `scopeOf()` 对空数组返回 `undefined`，`canRead` 随即全放行；UI 侧由 `src/modules/ai-assistant/index.tsx:151` 的 `runGuarded` 兜住 —— 未圈定时**不直接跑**，先弹「建议作用域卡」（`:149` 注释原话「**空 scope 在主进程侧 = 不设限**」）。

⇒ 由此得到两条**反直觉、但必须写下来**的结论（直接影响 `F-3` 方案）：

- **「全选全库」在当前模型里不可表达**：空前缀 `['']` 经 `isWithinVaultScope` **恒为 false**（`norm.startsWith('/')` 对正常 rel 不成立）⇒ 等于「什么都不放行」；而空数组虽 = 不设限，却与「全部取消」是同一个状态、且会被守卫拦去走建议卡。所以「全选」只能**枚举具体条目**（如全部顶层项），**不能**写成一条空前缀。
- **「全部取消」= 交还不设限**：它不会把范围变成「不允许」，只是回到「由建议卡接管」—— 所以它**不是危险操作**，但也不能当「缩小范围」来宣传。

## [ ] F-1 AI 助手「模型 / 思考强度」菜单被压成竖条（文字逐字折行）

> **★ 拍板（2026-10-16）**：**先不修，随台账攒批** —— 处置方向仍待定（届时在下方 A/B/C 里选）。截图为**工作台页面形态（宽宿主）**下的复现，即下方「与宿主宽窄无关」那条已由开发负责人实测确认。

**提出（2026-10-16，开发负责人原话）**：「发现了第一个bug了，AI助手的模型选择框比例显示不正确」（附截图）

**现象**：AI 助手输入区底部点模型按钮（显示「默认 ⌄」）弹出的浮层被压成约 70px 宽的竖条：

- 表头「回答模型 · 仅本任务生效」按 **4 字一行**折成 4 行；
- 每个模型行只看得见供应商名的头一两个字（截图里连续一排 `OpenCode` 全被截断，看不到模型名）；
- 底部「思考强度」折成竖排，四个强度按钮只剩最左一个可见，且它自身又折成「关 / 闭」两行。

**期望**：宽 280px、模型行一行一个、强度四档横排 —— 即 `src/modules/ai-teaching/index.tsx:2393` 那个**同款菜单**的正常形态。

**定位 / 根因**（静态审计，**未改码**）：

两处菜单**逐行同构，只差一个类**：

| 位置 | 弹层根节点类名 |
|---|---|
| `src/modules/ai-teaching/index.tsx:2393`（对照，正常） | `absolute bottom-full right-0 mb-1.5 w-[280px] z-30 …` |
| `src/modules/ai-assistant/index.tsx:446`（报障） | `… w-[280px] max-w-full z-30 …` ← 多这一个类 |

`max-w-full` = `max-width: 100%`，而百分比 `max-width` 是相对**包含块**解析的 —— 绝对定位元素的包含块是**最近的定位祖先**，这里是按钮外面那层 `<div className="relative">`（`ai-assistant/index.tsx:431`）。那层又是上一行 flex 行（`:429`，`relative flex items-center gap-2`）里的 **flex item**，宽度收缩到按钮本身 ≈ 70px（按钮内容 = `Bot` 图标 + `max-w-[140px] truncate` 的模型名，截图里模型名是「默认」两字）。

⇒ `w-[280px]` 被 `max-width: 100%`（≈70px）直接压掉；`px-3` 再占去 24px，正文只剩 ~46px，10.5px 字号**恰好一行 4 字** —— 与截图每处折行位置完全吻合。

**★ 与宿主宽窄无关（开发负责人已实测确认：截图为宽宿主形态）**：弹层浮在一片宽阔空白上（模块区域本身很宽），宽度照样被压 —— 因为 `max-w-full` 取的是**触发按钮的宽度**，与宿主无关。这也解释了它为什么没在别处暴露。

**引入来源**：`max-w-full` 由 `a71a97f`（v3.9.0 两个新模块，2026-10-16 16:06）随 AI 助手模块一起进来，**不是**本次 aiTeaching 合并引入的。

**性质**：真 UI 缺陷（弹层宽度解析错）。看起来像是「怕弹层溢出窄宿主」加的保险，但 `max-w-full` 不是干这个的工具 —— 它相对触发按钮，而不是面板。

**处置方向**（**拍板：先不修**，方向待选）：

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| **A. 最小改动** | 删掉 `max-w-full`，与 AI 教学对齐 | AI 助手有 `sidebarHosted` 托管形态（`ai-assistant/index.tsx:295` 走 portal 进宿主侧栏），宿主窄时 280px 弹层会从面板左缘溢出 |
| **B. 走仓库既有正解（推荐）** | 与 `AssistantEntry`（同一功能区的兄弟菜单）同款：`useAnchoredMenu`（`src/lib/useAnchoredMenu.ts`）+ `createPortal` 到 body | 改动大于 A；但该 hook 会按**实测高度**上下翻折、并把 `left/top` **clamp 进视口**，一次解掉「窄宿主溢出 + 被裁剪祖先吃掉」两类问题。先例：`docs/v3.4.0-feedback.md` F-2；`AssistantPanel/AssistantEntry.tsx:17` 原话「彻底脱离裁剪祖先」 |

**待补（拍板方向前唯一缺的信息）**：**窄宿主形态仍未验** —— AI 助手被托管进宿主侧栏时（`ai-assistant/index.tsx:295` 走 portal）弹层表现如何。这决定方案 A 是否可用；若窄宿主下 A 会溢出，则直接走 B。

## [ ] F-2 作用域面板：勾选目录后其子项显示未勾选；顺这个显示去点它也无任何反应

**提出（2026-10-16，开发负责人原话）**：「如果我勾选的是一个目录的话，我勾选的是顶层目录，然后我展开了这个目录我发现里面的条目是没有勾选的状态，如果这只是显示出错这个就很反直觉」

**现象**（两个症状、同一根因）：

1. 勾选顶层目录 `A` → 展开 `A` → 子项 `A/x`、`A/y` 的复选框**全是未勾选态**（用户怀疑「只是显示出错」—— 报告准确，但不止于此）；
2. 顺着这个显示去点 `A/x` 的复选框 → **什么都不发生**：不勾上、无 Toast、无任何反馈。

**定位 / 根因**（静态审计，**未改码**）：「显示口径」与「作用域语义」不一致，而不一致处还配了一个静默早退。

| 位置 | 代码 | 含义 |
|---|---|---|
| `src/modules/ai-assistant/ScopePane.tsx:82` | `const checked = scopeSet.has(rel)` | 勾选态 = 该 rel **是否为 scope 数组里的精确条目** |
| `electron/lib/kbStore/vaultScope.ts:23-30`（主进程真源） | `norm === p \|\| norm.startsWith(p + '/')` | 作用域语义 = **前缀覆盖**：勾中目录即覆盖其下全部 |
| `electron/lib/aiAssistantScope.ts:8` | 注释「归一化后的仓库相对前缀数组（目录前缀 + 单文件路径）；文件自身即其前缀」 | 同上 |
| `src/modules/ai-assistant/ScopePane.tsx:56-63` | 已选 → 删除；**被祖先覆盖 → `return`（静默）**；否则加为条目并清掉落在它内部的冗余条目 | 子项被祖先覆盖时 `onChange` **根本不会被调用** |

⇒ 语义是「覆盖」，显示是「精确条目」。**主进程侧的覆盖是真的** —— `canRead` / `canWrite` 都走 `isWithinVaultScope`，读写都按前缀放行。所以这不是「范围没生效」，而是**界面把它渲染成了没生效的样子**；再叠加那条静默 `return`，就变成「一个看着能点、点了没反应的控件」。**无反馈失效比显示错更伤**（同 `AGENTS.md` 里「加列漏 case = patch 静默丢弃、IPC 照样成功」那一类）。

**性质**：真缺陷（显示与语义口径不一致 + 可点控件静默无效）。**不是**有意设计 —— 第 60 行注释写的是「已被某个祖先目录覆盖 → 无需重复添加」，意图是去重，但它没把「已被覆盖」这件事表达给用户。

**处置方向**（待拍板）：

| 方案 | 做法 | 代价 / 风险 |
|---|---|---|
| **A. 让显示跟随语义（推荐）** | 派生一个展示态：被祖先覆盖的行显示为**已覆盖**（`indeterminate` 半选，或实勾 + 浅色 + 悬浮说明）；点击不再静默 —— 或提示「已包含在上层 xxx 内」，或把该子项**提升**为自己的条目（并从祖先条目里排掉它） | 只改 `ScopePane`；但要定「被覆盖行的点击语义」（提示 vs 提升）—— 这是真正需要拍板的分叉 |
| **B. 保守版** | 显示口径不动，把被覆盖行**禁用 + 注明**「已包含在上层」 | 治好了「点了没反应」，没治好反直觉（子项仍显示未勾） |
| **C. 改成真级联父子模型** | 父勾 = 子全勾（级联勾选/取消） | 改动最大：勾 200 个文件会产生 200 条 scope，与现有「前缀压缩」（`ScopePane.tsx:62` 专门清理内部冗余）的设计相悖，需重新对齐服务端语义 |

**与 F-3 的关系**：F-3 要的全选/全部取消会放大本条的观感（全选后展开一片「未勾」的子项）—— 两条建议同批修。

## [ ] F-5 已选项 chip 行把目录树整体下压；选得多了左栏显乱

**提出（2026-10-16，开发负责人原话）**：「选择了文件条目后 搜索框下会有被选择的文件条目将下面的内容整体向下挤，当内容多了左侧边栏看着就比较杂乱了」

**现象**：搜索框下面那排已选 chip（`ScopePane.tsx:133-150`，`flex flex-wrap`）高度**无上限**，每多选一项就多占一行；而它下方的目录树是唯一的滚动区（`:151`，`min-h-0 flex-1 overflow-y-auto`）⇒ chip 越长、树越矮，选到十几项时树基本被吃到看不见。

**定位 / 根因**（静态审计，**未改码**）：

| 位置 | 事实 |
|---|---|
| `src/modules/ai-assistant/index.tsx:211` | 整个作用域面板被限高 **`maxHeight: '56%'`**（相对侧栏）。chip 区与树的争抢发生在**一个固定的 56% 盒子里**，chip 每长一行都是从树上割 |
| `src/modules/ai-assistant/ScopePane.tsx:133-150` | chip 行 `mx-2 mb-1.5 flex flex-wrap gap-1`，**无 max-h / 无 overflow**，条目数无上限 |
| `src/modules/ai-assistant/ScopePane.tsx:151` | 树是 `min-h-0 flex-1 overflow-y-auto` ⇒ 被挤压方永远是树，且可被压到 0 高 |
| chip 内容 | 每个 chip 显示**整条 rel 路径**（仅 `truncate`），长路径下每行放不下几个 ⇒ 放大拥挤 |

⇒ 表层是「chip 太多」，根子是**同一份选择态被表达两次**（树里的勾 + 树上方的 chip 列表），而两次表达里**只有 chip 那份会挤压布局**。所以这不只是「给 chip 加个滚动」的问题 —— 要先问 **chip 列表值不值得占这块地方**。

**性质**：真 UI 缺陷（布局挤压）+ 信息架构冗余（同一状态双重表达）。

**处置方向**：已出可交互原型（见下「原型」节），五档逐条可点：

| 方案 | 做法 |
|---|---|
| **现状** | chip 无上限铺在树上 |
| **A. 定高 + 内部滚动** | chip 行封顶约 2 行 + `overflow-y:auto` |
| **B. 单行摘要 + 可展开** | 默认一行「已选 N 项 ▾」，点开才铺 chip |
| **C. 只报数（推荐）** | 一行「已选 N 项 · 全部取消」；**不再铺 chip**，选择态交给树内表达 —— 最降噪，直答「看着杂乱」 |
| **D. 停靠到树下方** | chip 区挪到树下：树的**顶部**不再被推走（观感稳定），但树高照样被占 |

**与 `F-2` 的关系（重要）**：两条其实在回答同一个问题 ——「选择态怎么表达」。`F-2` 管**树内**（被祖先覆盖的子项怎么显示），`F-5` 管**树外**（已选清单怎么占地方）。所以原型是**一份合并稿**，而不是两个原型。

## ★ 原型：AI 助手左栏统一改造（待体验拍板）

**位置**：[`tmp/ai-assistant-scope-pane-proto/index.html`](../tmp/ai-assistant-scope-pane-proto/index.html)（`tmp/` 已 gitignore，不进版本控制）

**一份稿同时演示四条**，右侧逐项切换对比，右上实时读数（目录树可视高度 / chip 区高度 / 已选条目数）：

| 簇内条目 | 原型里可切的档 |
|---|---|
| `F-5` 已选项占地方 | 现状 / A 定高 / B 摘要 / **C 只报数（推荐）** / D 停靠 |
| `F-2` 覆盖态显示与点击 | 现状（精确条目 + 静默）/ 补丁（半选 + 说明）/ **集合语义 + 前缀压缩（推荐）** |
| `F-3` 批量入口 | 全选顶层 / 全选可见 / 全部取消（+ 三条口径说明） |
| `F-4` 改名入口 | 现状（仅双击）/ **悬停铅笔（推荐）** / ⋯ 菜单 |

**★ 原型承载的核心设计主张**（比「给 chip 加滚动条」深一层）：

`F-2` 与 `F-5` 是同一问题的两半，而 `F-2` 的正解能顺带缓解 `F-5` ——
现状是「**精确条目**存储 + 精确条目显示」，于是覆盖态无处可显示（子项只能显示未勾），也必然需要 chip 列表去补表达（于是挤压树）；
改成「**集合语义 + 前缀压缩**」后：**显示 = 每个节点的真实归属**（实勾 / 半选 / 未勾），**点击 = 加入或移出该子树**，**存储仍是前缀**（复用既有的压缩逻辑，主进程语义不动）⇒ chip 列表天然变短。

**该主张已知代价（原型里可体验）**：前缀模型**没有「排除项」**，所以在大目录里单独取消一项，必须把该目录**炸开成子项**（`归档` → 它的每个子项各占一条），scope 条目数会变多、`buildScopeManifest` 拼给模型的清单也会变长。要根治得给 scope 模型加「负条目」，那是主进程改动（`aiScope` + 越权守卫），**不在本次原型范围**。原型里点「模拟「选了大目录再取消一项」」即可看到这个代价。

**配套深链**：原型支持 URL 参数，便于把某个方案组合直接发给别人，例如
`index.html?f5=treeonly&f2=set&f4=pencil&pick=20`（`f5` / `f2` / `f4` / `pick` / `open`）。

## [ ] F-1 勾选完成任务：点勾选框常变成「右栏弹开修改态」，修改态里没有完成开关；勾上后无完成反馈

**提出（2026-10-25，开发负责人，附截图）**：「今天」视图（2026-10-25 · 周日，6 条任务，完成 0）想对任务（「在 Linux 上安装 zcode」）勾选完成。原话：「想要对已经完成的任务进行完成勾选，点击后的反馈是右侧边栏显示修改态。好不容易勾选了完成的任务，结果还没有完成反馈」。截图佐证：右栏为该任务的编辑表单（含排期时段 `10/27 08:00–12:00`，即 N-1 场景同一条任务，时段已写入），列表 6 条全部未勾、顶部「完成 0」。

**现象拆三层**：① 点勾选框（的意图）得到的反馈却是右栏弹出该任务的修改态；② 反复尝试才真正触发一次勾选动作；③ 勾选后界面无完成反馈——条目仍在、勾选框仍空、完成计数仍 0。

**定位（2026-10-25 探查，未动码）**：

1. **「点勾选框 → 打开修改态」不是 stopPropagation 失效，是热区问题**：行组件勾选按钮本身有 `e.stopPropagation()`（`src/modules/schedule/components/ScheduleTaskRow.tsx:35`），点中按钮不会冒泡到行；但勾选框热区仅 16px（`h-4 w-4`），而行体整行可点开编辑（`onClick={() => onOpen(task)}`，`:30`）——点击偏出勾选框一丝就落在行体 → `openTask` → 右栏打开修改态，且右栏收起时 `revealPanel` 会直接弹开整个右栏（`src/modules/schedule/ScheduleUiContext.tsx:35-39`），反馈非常显眼，完全盖过用户「我只是想打个勾」的意图。
2. **修改态里没有主任务的完成开关**：`TaskPanel`（`src/modules/schedule/components/TaskPanel.tsx`）表单字段为标题/描述/日期/时间/标签/预估/排期时段，**无 status 切换**；仅子任务有完成 toggle（`:118-125`）。用户被弹进修改态后在那里找不到完成入口，只能回列表继续瞄准 16px 小框——「好不容易勾选了」即这个来回的成本。
3. **勾选动作本身零反馈，全靠广播刷新**：`handleToggle`（`src/modules/schedule/index.tsx:247-253`）只发 IPC，无乐观更新、无 Toast、无动效；界面刷新完全依赖主进程 `broadcastDataChanged('schedule')`（`electron/database/repositories/scheduleRepo.ts:164`）→ `useDataChanged('schedule')`（`index.tsx:100`）。对比同视图 `addTask` 成功后**手动** `onChanged()` 刷新（`TodayView.tsx:77`）——凡手动刷新的操作都有即时反馈，唯独勾选全押在广播时序上。
4. **成功表象本身也弱**：TodayView 只渲染未完成任务（`pending` 过滤，`TodayView.tsx:47-50`），勾选成功的正确表现是「条目瞬间消失 + 完成 +1」，没有划线/退场动效过渡（对照打卡模块 `TodoItem` 播完动画才回调的先例，`AGENTS.md` 铁律 7）。
5. **「自动保存覆盖」已排除**：右栏 `TaskPanel` 有 400ms 防抖自动保存（`TaskPanel.tsx:86-111`），patch 不含 `status`；主进程 `updateTodo` 为**合并语义**（未传字段保留原值，`electron/lib/kbStore/scheduleVaultRepo.ts:272-297`），不会把 done 冲回 pending。

**根因（分层）**：

- **落差（主因）**：完成操作全应用只有一个 16px 热区的入口（列表行内勾选框），右栏修改态无开关，热区又极易误触行体变成「打开编辑」——完成一个任务的命中成本过高。
- **感知缺陷**：勾选无乐观更新 / 无动效 / 无 Toast，广播有半拍延迟时表象就是「点了没反应」；即便成功也只是条目无声消失。
- **存疑（环境因素，待复现排除）**：截图的「完成 0」若在窗口重新聚焦（focus 会强制 refresh，`index.tsx:106-110`）或切走再切回模块后仍是 0，则盘上 status 就不是 done。嫌疑：**同机另一 AI 会话当时正在并发写 schedule**（该任务正是 N-1 场景任务，若 AI 以删建重建同任务，新行 status 重置 pending）。复现本条时先排除这条并发线。

**处置方向（待拍板）**：

- `TaskPanel` 表单头部加主任务「完成 / 重新打开」开关（与列表勾选同语义，toggle 后走 `onChanged` 刷新）。
- 勾选框热区扩大（视觉 16px 不变、命中区 ≥24px，用 padding / 伪元素扩热区）；或行单击与进编辑解耦（单击仅选中、双击或显式按钮才开编辑）——UX 取向需拍板，后者动静更大。
- `handleToggle` 改乐观更新：本地立即翻转 status，IPC 失败回滚 + Toast；done 条目移出列表时补 `.kb-item-out` 退场动效（走 `docs/ui-animation-plan.md` 既有令牌，铁律 13，先补基建再落码的口径适用）。
- 复现指引：勾选后切走再切回日程模块（触发 `isActive` refresh）看计数是否恢复；仍 0 则读 vault `.knowbase/modules/` 下 schedule 数据文件核对盘上 status，并确认当时是否有 AI 会话在写日程。

**状态**：`[x]` 已修（2026-10-25）。落码三件 + 一件未做：
- `TaskPanel` 表单头部加「标记完成 / 已完成·点击重新打开」开关（与列表勾选同语义，patch 仅含 status，与表单防抖自动保存互不干扰）。
- `ScheduleTaskRow` 勾选框命中区 16→28px（视觉圆 16px 不变，负 margin 补偿占位）。
- `handleToggle` 改乐观更新（本地即时翻转 + 失败回滚 Toast）；`TodayView` 刚完成条目原位保留一拍播 `.kb-item-out` 退场（约 180ms，播完移除；分组计数不含退场条目）。
- 未做「行单击与进编辑解耦」（处置方向里标注需拍板、动静较大的备选，热区扩大已消除主要误触）。

## [~] N-1 AI 写入类工具「单次运行 7 次」上限应提为可配置（复杂任务被腰斩）

**提出（2026-10-25，开发负责人）**：让 AI 助手把「下周二 10/27 08:00–12:00」排进日程时间格，AI 调 `update-todo` 时返回「已达本次会话写入操作上限（7 次）」，该时段未写入；同批要做的「第二个答辩（另一作业）的任务与工作流」也因额度耗尽未创建。原话定调：「这个应该要设置成一个可被设置的数值，因为如果这个次数限制这么小，AI 无法完成比较复杂的任务」。

**现象**：一次任务里 AI 连续做多个写操作（建任务 / 排期 / 建工作流一串），第 8 个写工具调用（`update-todo`）被拦下——不执行、不落盘，回喂错误 JSON 要求模型「停止写入并总结」，任务被腰斩。用户侧还产生了「需等额度恢复」的误解（见根因第 2 条：实际无等待一说）。

**定位（2026-10-25 探查，未动码）**：

1. **上限是硬编码常数**：`MAX_SESSION_WRITES = 7`（`electron/lib/agentService.ts:94`），不在 `src/lib/settings.ts`，用户不可调。
2. **作用域与文案不符——「本次会话」实为「本条消息的一次运行」**：计数变量 `sessionWrites` 与 agent 循环同函数作用域（`electron/lib/agentService.ts:1359`），生命周期 = 一次用户消息触发的完整 run（最多 `agentMaxRounds` 轮）；计数**不落盘、无时间恢复机制**——下一条新消息即从零重计。报错文案「已达本次会话写入操作上限」（`agentService.ts:1655`）与失败分类文案（`electron/lib/llmFailurePure.ts:411`）都在说「会话」，把「每条消息重置」的机制说成了「会话级配额」，直接制造了「等额度恢复」的误解。
3. **计入范围**：`requires: 'write'` 的写工具集合 `writeTools`（`electron/lib/agentService.ts:555` 动态构建，`tool.request` 启用新写工具后立即生效）；读类工具不计次，只受轮数 / token 预算约束。拦截点在 `agentService.ts:1647-1657`（`runSingleToolCall` 内判定 + 回喂）。
4. **防失控三层里唯一不可调的一层**：轮数（`agentMaxRounds`，默认 16，可配 2-64，`src/lib/settings.ts:217`）与 token 预算（`agentRunTokenBudget`，默认 500000，可配，`src/lib/settings.ts:218`）都已设置化，唯独写次数上限是硬编码。

**根因**：7 次的本意是防失控循环刷盘（单次请求内写上限，注释见 `agentService.ts:1645`），量级按「普通任务」定；但「一次 run 内建多个任务 + 排期 + 工作流」的正常复杂任务轻松超过 7 次写入，保护上限变成了任务能力上限。

**处置方向（已拍板：提成设置项）**：

- 照 `agentMaxRounds` 的路子：`src/lib/settings.ts` 新增 `agentMaxSessionWrites`（进「Agent 循环」组、`section: 'aiTools'`、`affects: 'live'`）；收敛函数放 `electron/lib/agentLoopPolicy.ts` 与 `clampMaxRounds` 并排；`agentService.ts:1396` 附近读设置替换硬编码常数；设置界面在 `src/modules/settings/views/AiToolsView.tsx`「Agent 循环」组加控件（参考 `agentMaxRounds` 控件 `AiToolsView.tsx:399-414`）。
- **顺带修文案**（两处）：`agentService.ts:1655` 与 `llmFailurePure.ts:411` 的「本次会话写入上限 / 本次会话写入操作上限」改为「本条消息的写入操作上限」一类的措辞，消除「等额度恢复」误解。
- 默认值是否维持 7 还是直接抬高（如 16 / 20），实现时拍板。

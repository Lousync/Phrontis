# A. 批量移动原语

## A1. 目标

让 AI 用**一次工具调用**提交多条文件移动，落成**一个变更方案 op**，用户看到**一张方案卡**，一次确认完成整批移动。

要解决的不是“AI 不会搬文件”，而是：

- N 个文件 = N 次工具调用 + N 条 plan op + N 次写操作计数；
- 默认写入上限 20（上限 99），稍大的整理任务直接撞顶；
- 方案卡出现 100 行逐条变更，用户无法快速判断“它到底要把什么搬到哪”；
- 逐文件搬带附件的笔记会断相对链接；AI 教学目录还可能破坏课程结构。

## A2. 非目标

- 不做 UI 文件树的多选批量移动（本方案只解决 AI 侧）。
- 不开放任意文件类型：v1 只允许 `.md` / `.txt`。
- 不做目录移动：v1 只搬文件；目录移动放 P1（见 A9）。
- 不把 `terminal.exec` 包装成批量移动入口。
- 不自动改写 Markdown 里的相对附件链接。
- 不改 `fileOpHistory` 的 Ctrl+Z 语义（整批撤销走方案卡的「回滚整任务」，见 A7）。

## A3. 现状

- 唯一通用移动工具：`builtin.vault.rename`（`electron/lib/builtinTools.ts`，`path` + `newPath`，一次一个文件）。
- 只接受普通区 `.md` / `.txt`；`.knowbase`、隐藏目录、附件、目录都不在 AI 写白名单（`isAiWritableFile`）。
- `tier: 'ondemand'`：模型要先 `builtin.tool.request` 申请。
- 每次 rename 都计入 `agentMaxSessionWrites`（默认 20，上限 99）。
- 变更方案层已经支持多条 op 批量应用（`ReviewPane` 全选 + 「应用 N」），但那是 N 条独立 op，不是批量工具。
- 底层 `renameWorkspacePath()` 支持目录；`migrateCourseLayoutTo()` 已有批量目录移动 + 暂存换位的成熟算法，可复用其思路。

## A4. 工具设计

### A4.1 注册信息

```ts
name: 'builtin.vault.move'
title: '批量移动/重命名仓库文件'
description: '一次移动或重命名多个仓库内 .md/.txt 文件（最多 100 项）。先全量校验再暂存为一条变更；目标已存在、路径非法、越界、隐藏目录、AI 教学目录会整批拒绝。'
source: 'builtin'
enabled: true
readOnly: false
requires: 'write'
tier: 'ondemand'
vaultFile: 'write'
```

- 必须加入 `builtin.tool.request` 的 description 工具清单。
- 单工具 schema 控制在 800 字符以内（AGENTS.md 铁律 16）。

### A4.2 入参

只保留一种形状，避免模型在 `targetDir` / `paths` / `moves` 之间选错：

```json
{
  "type": "object",
  "properties": {
    "moves": {
      "type": "array",
      "minItems": 1,
      "maxItems": 100,
      "items": {
        "type": "object",
        "properties": {
          "from": { "type": "string" },
          "to": { "type": "string" }
        },
        "required": ["from", "to"]
      }
    }
  },
  "required": ["moves"]
}
```

- `to` 是已存在目录 → 移入该目录，保留原文件名；
- `to` 是新路径 → 按新文件名移动/重命名；
- 不提供 `targetDir` 快捷参数：模型对每个文件重复同一个目录即可，schema 更简单、预检更明确。

### A4.3 预检（先全量，再暂存）

任何一条失败 → **整批不暂存**，一次性返回全部冲突，让模型在同一轮改参数重试。不要“先搬能搬的”。

规则：

1. `moves` 1–100 条；`from` / `to` 去空白、`\` 归一为 `/`。
2. `from !== to`；`from` 不重复；解析后的 `to` 不重复（Windows 下按大小写不敏感比较）。
3. `from` 必须在仓库内、首段不以 `.` 开头、扩展名 `.md` / `.txt`、存在且是文件。
4. `to` 必须在仓库内、首段不以 `.` 开头；若是已存在目录 → 解析为 `to/basename(from)`；否则必须以 `.md` / `.txt` 结尾。
5. 解析后的目标不得已存在（v1 不支持覆盖；大小写-only 重命名也先拒绝，避免 Windows 临时改名复杂度）。
6. 禁止 `AI教学/` 下的路径：课程/会话目录有 `.session.json` 锚点、课程大纲路径等不变量，必须走 `migrateCourseLayoutTo()` / `course.*` 专用通道。
7. 禁止 `.knowbase/`、`.attachments/` 等隐藏目录；禁止 `..` 越界（走 `resolveSafe`）。
8. 目标父目录不存在时允许自动补建（与 `renameWorkspacePath` 的 `mkdir -p` 语义一致）。
9. 失败返回结构化冲突列表：`{ index, from, to, reason }[]`；错误文案按条编号，方便模型逐条修正。

### A4.4 暂存

- 通过 `commitOrStage(ctx, makeOp, run)` 走统一岔口。
- propose 模式：只落**一条** op：

```ts
{
  kind: 'move-batch',
  moves: [{ from, to }, ...],
  summary: '移动 23 个文件 → 第2章/知识点A（示例：a.md、b.md…）'
}
```

- 非 propose 模式：直接执行整批（同样先预检）。
- 工具返回（暂存态）：`{ ok: true, staged: true, opId, count, summary }`。
- 工具返回（直执行）：`{ ok: true, moved, items: [{ from, to, ok, error? }] }`。

### A4.5 ChangePlan 类型扩展

`electron/lib/aiAssistantPlanPure.ts`：

```ts
export type PlanOpKind = 'write' | 'edit' | 'rename' | 'trash' | 'mkdir' | 'tag' | 'tool' | 'move-batch'

export interface PlanOp {
  // ...现有字段
  /** move-batch 专用：整批移动条目 */
  moves?: Array<{ from: string; to: string }>
}

export interface FsAction {
  action: 'write' | 'rename' | 'trash' | 'mkdir' | 'move-batch'
  relPath: string
  content?: string
  to?: string
  /** move-batch 专用 */
  moves?: Array<{ from: string; to: string }>
}
```

`src/types/index.ts` 的 `AiPlanOpKind` / `AiPlanOp` 同步镜像（两处必须一起改）。

### A4.6 应用与回滚

- `actionForOp(op, 'apply')` → `{ action: 'move-batch', moves: op.moves }`。
- `actionForOp(op, 'rollback')` → `{ action: 'move-batch', moves: reverse(op.moves) }`。
- `aiAssistantPlan.ts` 的 `runAction` 增加 `move-batch` 分支，调用 `applyMoveBatch(rootPath, rootId, moves)`：
  1. **应用前再预检一次**（暂存后磁盘可能已变）；有冲突 → 整批不执行，抛结构化错误。
  2. 顺序执行；单条失败 → 逆序回滚已移动的条目。
  3. 回滚成功 → 抛「整批未应用（已回滚）」；回滚失败 → 抛「部分残留」并列出仍在新位置的路径。
  4. 全部成功 → 返回 `{ moved, items }`。
- `applyPlan` 的 `refresh(rels)` 对 `move-batch` 要收集**所有** `from` / `to` 的父目录，不能只取第一条。
- `rollbackTask` 目前对 `runAction` 没有逐 op 容错；`move-batch` 回滚要包 try/catch，失败时把 `op.status` 标为 `failed` 并写 `error`，不能中断整个任务回滚。
- 成功/失败都广播 `knowledge` + 文件树刷新（`invalidateIndexIfCurrentVault` 已在 `renameWorkspacePath` 内）。

### A4.7 UI（方案卡）

`src/modules/ai-assistant/ReviewPane.tsx`：

- `KindIcon` 增加 `move-batch` → `MoveRight`。
- `labelOf` 用 `op.summary`，不要拼 100 个路径。
- `isDiffable` 对 `move-batch` 返回 false。
- 新增 `MoveBatchView`：
  - 按目标目录分组；
  - 组头显示「→ 目标目录 · N 个文件」；
  - 组内每行 `from → to`，超长省略，`title` 显示完整路径；
  - 顶部显示总数、冲突预检已通过、示例路径；
  - compact 模式单列可滚动，不挤压右栏。
- 勾选语义：**一条 op = 一个勾选框**，整批应用/整批丢弃；v1 不做逐文件取消。用户想排除某几条 → 让 AI 重新提交。
- 应用成功后 Toast 只报「已移动 N 个文件」；整批撤销走现有「回滚整任务」，不在 `fileOpHistory` 里再记一遍，避免双撤销。
- 失败时列出「已移动 / 未移动 / 回滚失败」；不要只报一个总数。

### A4.8 写上限与审计

- 整批算 **1 次写操作**（一次工具调用），但用 **单次 100 条硬上限** + **单条消息累计 300 条硬上限** 兜底。
- 这是对 `agentMaxSessionWrites` 的有意例外：批量工具本身是有界操作，不应按文件数消耗 20/99 的防失控预算；但也不能让模型用 99 次批量调用绕过上限。
- 累计上限由 `agentService` 在工具返回后按 `itemCount` 记账：`move-batch` 返回 `{ moved, count }`，单条消息内累计 `count > 300` 时拒绝后续批量移动，提示模型拆到下一次消息。
- 审计仍走 `aiTools` 的 `tool.stage` / `tool.invoke`；`summarizeArgs` 只保留前 200 字符，完整 `moves` 在 plan JSON 里，排障时以 plan 文件为准。
- 如果后续要更细的审计，可加一条 `vault.move.batch` 专用记录（`count` + 目标目录 + 示例），但 v1 不新增审计通道。

### A4.9 目录移动（P1，不在 v1）

- v1 只搬文件，避免一次性打开目录/附件/链接重写的权限面。
- P1 再加 `allowDirs`（或独立 `builtin.vault.move-dir`）：
  - 复用 `migrateCourseLayoutTo` 的暂存区 + 换位算法；
  - 预检禁止把目录移进自己的子树；
  - 目录移动天然保留相对链接，是“带附件笔记整理”的正确单位；
  - AI 教学目录仍走专用迁移，不走通用工具。

# B. 全局关闭拼写检查

## B1. 目标

应用内**任何可编辑区域**都不出现浏览器拼写检查的红色波浪线：AI 教学简答题、AI 对话输入框、笔记编辑器、设置输入框、密码本、书签表单、日程表单、日签小窗、密码填充浮窗，一处也不出现。

## B2. 现状与根因

截图位置是 AI 教学 / 知识库的简答题作答框：

- `src/components/shared/ShortAnswerCard.tsx` 的 `<textarea>` **没有** `spellCheck={false}`；
- 输入 `DMA` 被 Chromium 拼写检查标红。

但这不是单点问题（当前源码快照）：

- 全仓 25 个 `<textarea>`，其中 14 个没有 `spellCheck`；
- 243 个 `<input>`，其中 127 个文本类没有 `spellCheck`；
- 逐个补属性不可维护，而且新组件很容易再漏。

根因是 Electron 的窗口级开关：

- `BrowserWindow.webPreferences.spellcheck` 默认 `true`；
- 三个 `BrowserWindow` 都没有显式关闭；
- Chromium 的拼写检查是 **per-webContents** 的，子 frame / iframe 共享同一开关，所以窗口级关闭就能覆盖全部渲染内容。

## B3. 修复方案

### B3.1 主修复：三个窗口全部关闭

在以下三个 `BrowserWindow` 的 `webPreferences` 中加 `spellcheck: false`：

- `electron/main/index.ts` 主窗口；
- `electron/main/dayPanelWindow.ts` 日程小窗；
- `electron/main/passwordFiller.ts` 密码填充浮窗。

```ts
webPreferences: {
  preload: ...,
  sandbox: true,
  contextIsolation: true,
  nodeIntegration: false,
  spellcheck: false,
}
```

这是唯一的根开关；设置后，即使某个 `<textarea>` 没写 `spellCheck={false}`，也不会出现红色波浪线。

### B3.2 第二层：根文档继承

`index.html` 的 `<html>` 加 `spellcheck="false"`：

```html
<html lang="zh-CN" spellcheck="false">
```

`spellcheck` 属性会被可编辑后代继承；作为窗口开关之外的兜底，不替代窗口开关。

### B3.3 第三层：截图位置显式声明

`src/components/shared/ShortAnswerCard.tsx` 的 `<textarea>` 加 `spellCheck={false}`。这一条是“意图声明”，让后来的人知道这里明确不要拼写检查，不是漏了。

### B3.4 不做的事

- 不逐个给 127 个 `<input>` 补 `spellCheck={false}`；窗口开关已经覆盖，逐个补只会制造维护噪声。
- 不使用未公开的 Chromium 命令行开关；`webPreferences.spellcheck` 是 Electron 公开 API。
- 不处理 DevTools 自身的拼写检查（那不是应用内容）。
- 不新增用户设置项；这是产品级“一律关闭”，不是可配置项。

2. 断言 `index.html` 的 `<html>` 含 `spellcheck="false"`。

### K-1 笔记里按 `Ctrl+0` 会写到后台那本书的进度

> **★ 已修（2026-10-13，与 K-2 同批）**：可见性守卫从「只长在命令面板那条通道」扩到**阅读器自己的键盘 handler** —— 读不到可见根节点就整体早退（连翻页键一起守，不止缩放键）。改法、契约与锚漂移处理见 `docs/ui-updates.md` §50。

- **现象**：书架 Tab 里开着一本书（没在读，切到笔记了），笔记里另开着一个 PDF 附件。此时按 `Ctrl+0`，后台那本书的阅读状态里被写进一条 `zoom: 1`。
- **根因**：Tab 是 `display:none` 保活（不卸载），所以两个 `PdfReaderView` 实例同时挂着。阅读器的 `Ctrl+0` 分支是**无条件的 window keydown**（`src/components/shared/pdf/PdfReaderView.tsx` 的快捷键 effect），它对「我在不在屏幕上」毫无判断。而 `resetFit()` 末尾 `scheduleProgress({ zoom: 1 })` 会在 800ms 后**落盘**（`pdfReaderPatch`）。
- **处置方向**：把 2026-10-13 给命令面板通道加的可见性守卫（`rootRef.current.offsetParent === null` ⇒ 所在 Tab 已收起 ⇒ 直接 return）同样加到键盘分支上。**约 1 行**，加完把 `verify-palette-channels.mjs` §3 的断言扩到键盘路径。

### K-2 笔记里的 `Ctrl+=` / `Ctrl+-` 双重缩放

> **★ 已修（2026-10-13，与 K-1 同批）**：让位判定改成并列两条 —— ① 书架 Tab + 开着书（原样）；② 屏幕上有**可见的** `PdfReaderView`（新增探针 `src/components/shared/pdf/pdfEvents.ts` 的 `hasVisiblePdfReader()`：App 侧拿不到笔记侧实例的 relPath，只能问可见性）。契约把「探针标记两侧对账」也一起锁了。见 `docs/ui-updates.md` §50。

- **现象**：笔记里打开 PDF 附件后按 `Ctrl+=`，**PDF 页面放大一档、整个界面也放大一档**。
- **根因**：`src/App.tsx` 的全局缩放在 `bookshelfReading && activeTab === 'bookshelf'` 时让位（那行注释写的是「正在书架里读 PDF 时」）—— 这是「阅读器只有一个挂载点」时代的判据。后来阅读器多了笔记编辑器里那个挂载点（`PageEditor.tsx`），让位判定没跟着放宽，于是两个 window keydown 监听器都会动作（`preventDefault()` 拦不住另一个监听器）。
- **处置方向**：让位判定改成「有可见的阅读器在读」而不是「书架 Tab 在读」—— 与 K-1 同一套可见性判据（`offsetParent`），两处一起修最省。**约 1 行**，加完补一条契约锁住「笔记侧挂载点也让位」。

### K-3 面板在没开 PDF 时也列「PDF 适应窗口」

- **现象**：笔记里看着普通 Markdown 页面，命令面板搜「适应窗口」能搜到「PDF 适应窗口」，点了没反应。
- **根因**：面板门控是**声明式**的（`requires`），只表达「哪个模块 Tab 激活」；「那个 Tab 里当前有没有开着 PDF」不是它能表达的东西。而笔记侧那个阅读器实例的存在与否只有 `PageEditor` 知道，App 侧的 `PaletteContext` 拿不到 —— 现在加维度只会做出「书架侧准、笔记侧不准」的半截口径。
- **处置方向**：**先挂着**。真要收紧，得先让知识库模块把「当前页是不是 PDF 阅读态」上报给 App（`PaletteContext` 加一个维度），那是一处新接口，值得单独一轮。

### K-4 键帽 DOM 不统一（`<span>` vs `<kbd>`）

- **现象**：设置 → 快捷键页的键帽是 `<span>`，启动空态的键帽是 `<kbd>`。视觉一致，读屏与语义不一致。
- **处置方向**：**暂不修**。空态那三条提示有一份 42 项断言的契约在守，为纯语义收益去动它不划算；等哪天因别的原因改到那一段时顺手统一。
- **★ 2026-10-13 追加**：为对比度整改（见 **F-2**）确实动到了这几处 —— 但**只统一了「颜色语义」**（四处共用 `.kb-kbd`），**DOM 仍是 `<span>` / `<kbd>` 两态**（语义统一仍未做，理由同上）。

### K-5 `Ctrl+O` 撞键（已修，留档）

- **现象**：`Ctrl+O` 同时被知识库「快速打开文件」和博客「切换大纲」占用，按一次跑两个动作。
- **处置**：博客大纲改 `Ctrl+Alt+O`（真源 `blog-outline`），2026-10-13 随「指令表对账」一起落码。**留在这里是为了记住这类问题的发现方式**：真源契约 §6 现在会强制「凡被两条以上命令共用的键位必须写 `conflictNote`」，机器可查。

### K-6 书架里读 EPUB / TXT 时那三枚缩放键没有任何效果

> **发现方式（值得记）**：K-2 要动那行让位判据，顺手把三个阅读器的键盘分支都读了一遍 —— 于是看出这条。**它是 K-1 / K-2 的同族问题**（「让位给阅读器」这个判断在阅读器变多之后没人复核过边界），但不是同一处：K-2 放宽的是「除了书架那本 PDF，还有谁也在这边读 PDF」；这一条在于**让位判据根本没看书的类型**。

- **现象**：书架 Tab 里开着 EPUB 或 TXT 在读，按 `Ctrl+=` / `Ctrl+-` / `Ctrl+0` —— 界面缩放被让位（`src/App.tsx` 的判据只要求「`bookshelfReading` 存在 + 书架 Tab 激活」，**不看 `kind`**），而这两个阅读器都没有对应的键：EPUB 的宿主键盘处理对 `ctrl/meta/alt` 一律 `return false`（`src/components/shared/epub/EpubReaderView.tsx:623`），TXT 阅读器没有带修饰键的分支（它只有工具栏的字号控件 + `fontScale`）。⇒ 这三枚键在 EPUB / TXT 阅读态下**没有效果**。
- **★ 未验证的那半句（如实记）**：这三枚键会不会落到**引擎级缩放**没有确认 —— 主进程只锁了视觉缩放（`electron/main/index.ts:281` 的 `setVisualZoomLevelLimits(1, 1)`），键盘那条是否仍被 Chromium 自己接管要真机按一下才知道。若真落到引擎缩放，表象更隐蔽：「界面确实变大了，但设置里的缩放值没动，而 `Ctrl+0` 又能把它复位」。
- **处置方向（待拍板，先不动码）**：两条路 ——
  1. **让位判据加类型**（`bookshelfReading.kind === 'pdf'`）：EPUB / TXT 阅读态下这三枚键归**界面缩放**（与在别处一致）。改动最小、语义最直白，代价是承认「EPUB / TXT 没有页面缩放快捷键」。
  2. **给 EPUB / TXT 补键**：EPUB 接它既有的字号 / 缩放档（工具栏已有按钮），TXT 接 `fontScale` —— 与 PDF 口径统一（「读到书时这几枚键归这本书」），但要新写两处键 + 契约，并先想清楚「字号」和「缩放档」哪个才算「放大」。

### F-1 吉祥物装了却选不到具体角色

> **★ 已修（2026-10-13，只修"确定"的那一半）**：设置页不再把「读不到清单 / 装了没启用 / 插件没加载起来 / 已启用却没读出来」四种情况都写成「尚未安装吉祥物角色」—— 现在五种空态各自一句可照做的提示（详见下面「处置方向」第 3 条与 `docs/ui-updates.md` §47）。**根因（开发者机器上为什么扫不到角色）仍待回报**：环境类原因（dev 主进程没重启 / 插件未启用）不可能由代码单方面确认。

- **反馈（2026-10-13，开发者原话）**：「现在的吉祥物为什么我安装了但是设置里不支持多款切换」

### F-6 让日程助手设在「周六」，日程表上落在「周日」

- **反馈（2026-10-13，开发者原话）**：「日程助手在设置任务的时候我让他设定的是周六，但是日程表上实际设置确实周日，不排除是底层工具的问题」。
- **★ 已核的证据（2026-10-13 只读调查）——全仓内部口径其实是一致的，偏差只可能来自**「模型给的数字」**：
  - 工具契约：`electron/lib/builtinTools.ts:1144` / `:1150` 明写 **`weekdays`：0=周一…6=周日**（`update-recurring` 同款，`:1191`）。
  - 生成侧：`src/lib/scheduleRecurringPure.ts:26-27` `weekdayMon0(d) = (d.getDay() + 6) % 7` ⇒ **周一=0**；`:52` 的人话标签 `WEEKDAY_CN` 也是周一起。
  - 手动面板：`src/modules/schedule/components/RecurringRulesPanel.tsx:89` 的星期钮走 `WEEKDAY_LABELS`
    （`src/modules/schedule/timetable.ts:148` = `['周一', …, '周日']`）⇒ 同样 **周一=0**。
  - ⇒ **三处内部口径一致**，所以「周六变周日」不是渲染换算错，而是**传进来的数字本身就差了 1**。
- **最可能根因（推测，但方向明确）**：模型天然按 JS `Date.getDay()` 想事情（**周日=0 … 周六=6**），
  而我们这套契约用的是**周一=0**（周六=5）。模型按自己的习惯传 `6` 表示周六 ⇒ 落到我们这里就是**周日** —— 正好差一天、正好是用户看到的现象。
  两个放大器让它一路静默：
  1. `builtinTools.ts:1169` `args.weekdays.map((n) => num(n, 0))` + `scheduleVaultRepo.ts:344-346` `normWeekdays` 只做 `clampInt(0,6,0)` 与去重排序 ⇒ **任何越界/非法值都被悄悄夹成合法值**，没有"你传的星期几我理解成了哪天"的校验或回显；
  2. **工具返回值不回显 weekdays**（`builtinTools.ts:1177` 只回 `id/title/freq/start/end`）⇒ 模型无从自查，用户也只能到日程表上才发现。
- **★ 铁证：模型自己在会话里承认了（2026-10-13 只读核对会话日志）**。日程助手那条会话
  （`%APPDATA%\knowbase\data\agent-messages\456bd58e-….jsonl`，唯一 `source=schedule` 的那条）17:29:23 那条的 `processText` 原文：
  > 「你说得对，是我的错：工具里 0=周一…6=周日，**我填了 6**，实际落在了周日。正确应为周六 = 5。现在改正：」

  随后 3 次 `update-recurring` 把值改回 5；17:25:43 首次创建时是 3 次 `create-recurring`。
  ⚠️ **所以磁盘上现在的 `weekdays: [5]` 是"修好之后"的值** —— 拿它反推会误判成"没问题"（我就是先读了磁盘、再看到这条日志才把因果钉死的）。
- **★ 一处与用户描述不同的地方（如实记）**：10/13 那份 `todos.json` 是空的（见 F-5）⇒ **屏幕上根本没有待办落在周日**；
  用户看到的「周日」只能是**左栏「🔁 固定日程」规则行的人话标签**（`src/lib/scheduleRecurringPure.ts:54-61` 取 `WEEKDAY_CN[6]` = 周日），
  **不是周网格把列画错了**（网格列按日期串定位，`TimetableView.tsx:156-159`）。⇒ 现象是「规则被标成周日」，不是「格子画在周日」。
- **处置方向（待拍板，未动码）**：
  1. **换一套不靠记忆的入参**：`weekdays` 收**字符串**（`['周六']` / `['sat']`）或 **ISO 1..7**（1=周一…7=周日）——
     0=周一 这种"自造刻度"是这类差一天问题的温床（本仓其它地方一律 `(getDay()+6)%7` 现算，只有**跨进程的契约**需要人/模型记住刻度）；
  2. **返回值回显**：`create/update-recurring` 把 `weekdays` 按人话回显（「每周六 14:00–15:00」），模型当轮就能自查、用户当场就能发现；
  3. **越界不静默**：`normWeekdays` 现在把非法值夹成 0（周一）—— 至少应拒绝或回一条警告，别让它变成一条"看起来正常"的错规则。
  取向：**1 + 2 一起做**（入参不再靠记忆 + 返回值可自查），3 作为防御。
  - **另有一处口径印证（第五处）**：契约 `.AGENT/scripts/schedule/verify-schedule-recurring.mjs:21/:35/:42` 用 `[5]` 断言「每周六」（2026-10-10 是周六）
    ⇒ 存储 / 生成 / UI / 契约**四处一致**，所以偏差只可能来自传进来的数字 —— 这也是本条能一次钉死的原因。
  - **软件侧确有责任的两点（本轮实测确认，其余是"不直观"而非"算错"）**：① 返回值**不回显 weekdays**（`builtinTools.ts:1177`）⇒ 模型首轮还自信地回复"每周六"，无从自查；
    ② `normWeekdays` 把越界值**静默夹成周一**。这两条是**要改**的；而入参刻度改成字符串 / ISO 1..7 属于"降低复发概率"的根治。

### F-7 笔记区：从「空文件」切走，切过去的那页不显示内容

- **反馈（2026-10-13，开发者原话）**：「从一个空文件切换到其他文件的时候，切过去的那个文件不显示内容，但是如果是从一个有内容的文件切到其他文件就会显示内容」。
- **★ 已核的代码事实（只读，2026-10-13）**：`loadPage` 在**取不到页面时不设置任何状态、也不清空内容**，界面就**停在上一页的正文**上：
  - `src/modules/knowledge/components/PageEditor.tsx:750-787`：`getKnowledgePageById(pageId).then(p => { if (p) { …灌 content… } else if (pageRef.current) { …重试/onBack… } })`
    —— `if (p)` 之外**没有任何"加载中/取不到"的分支去动 `content`**；
  - 同一个文件 `:779-786`：取不到页面时**每个 pageId 只重试一次**（`retryRef` 是**单槽** ref，`setTimeout(loadPage, 500)`），
    再失败就 `onBack()` —— 注释自己写着「可能是删除/转草稿，也可能是索引尚未重建（新建/转正后立即打开）」。
- **最可能的根因（推断，但能解释"为什么偏偏是空文件"）**：**这不是"新页不显示"，而是"加载失败时静默停在旧内容"** ——
  从**空**文件切走时，停在旧内容 = 停在**空白**，于是看起来像"新文件没内容"；
  从**有内容**的文件切走时，停在旧内容 = **上一页的正文还在**，于是看起来"正常显示"。
  ⇒ 两条症状其实是**同一个 bug 的两种表象**，而"从有内容的文件切过去会显示内容"很可能是**假正常**（显示的仍是上一页）。
- **第二条线索（与"空文件"直接相关）**：**空 / 新建文件往往没有 frontmatter `id`**，它们的页签 id 是 `draft:<relPath>` 伪页
  （`src/modules/knowledge/index.tsx:1006` / `:1011` / `:2636` 三处；模块侧另有「未转正」概念，`:926`），
  而这类身份与索引之间本来就有"转正/重建"窗口 ⇒ 切页那一瞬 `getKnowledgePageById` 查不到是**有理由发生的**，命中上面的重试/`onBack` 分支。
- **验证手法（三步，任何一步都能定性）**：
  1. **从空文件切到一个"内容明显不同"的文件**：若正文是空白 ⇒ 坐实「停在旧内容」；
  2. **从有内容的 A 切到有内容的 B**：核对正文与标题**是不是 B 的** —— 若还显示 A 的正文，则这条 bug 一直都在，只是从空文件切走时才显眼（**这是最该先做的一步**）；
  3. 在 `PageEditor.tsx:779` 的 `else if (pageRef.current)` 分支加一行日志（或断点），看切页时是否命中"取不到页面"。
- **处置方向（待拍板，未动码）**：
  1. **加载期必须有明确状态**：切页时要么清空正文并给加载态（骨架/空态），要么把"取不到"与"还没加载完"分开 ——
     现在的写法（什么都不做）在语义上等于「把上一页的内容留在屏幕上」，是最容易被误读成"新页是空的"的形状；
  2. **重试与兜底要分清两件事**：「索引尚未重建」应重试（次数/时长可放宽），「页面真没了」才 `onBack()`；
     `retryRef` 单槽在快速连点时会被覆盖，值得一并看（连点两个页签时谁的重试被吃掉）；
  3. 若确认与 `draft:` 伪页的转正窗口有关，则要在**转正后把页签 id 从 `draft:<rel>` 收敛到真 id**（或让查不到 draft 页时直接走 `loadDraftPage`），别让"身份切换"落在用户切页的那一瞬。

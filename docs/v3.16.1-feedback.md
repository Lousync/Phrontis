## [~] F-1 AI 教学长 agent 运行 → 渲染进程 OOM，窗口只剩透明框

### 现象

1. 应用在后台放一段时间后，再次点任务栏 / 托盘 / 应用图标，Phrontis 窗口「又出现了」，但**只剩一个透明的圆角窗框**：
   - 没有标题栏、没有内容、没有报错；
   - 窗口仍能被聚焦 / 拖动 / 关闭；
   - 托盘图标仍在，主进程没有退出。
2. 用户视角很容易判断成「Linux 桌面环境把窗口画坏了」或「应用自己卡死了」。
3. 实际是**渲染进程已经崩溃**，主进程和窗口对象还活着；透明窗口没有内容可画，就只剩透明表面和阴影。

### 证据

#### 1. 崩溃日志：renderer crash，exitCode 133

`/home/lousync/.config/knowbase/crash-log.txt`：

```text
[2026-11-02T00:39:47.491Z] render-process-gone v3.16.0
reason=crashed exitCode=133

[2026-11-02T01:15:39.521Z] render-process-gone v3.16.0
reason=crashed exitCode=133
```

对应本地时间 **08:39:47** 与 **09:15:39**。`133` = `SIGTRAP`，是 V8 主动 fatal，不是普通 segfault。

#### 2. journal：Oilpan 堆耗尽，JS heap 只有 31.4 MB

同一秒的 systemd user journal：

```text
V8 process OOM (Oilpan: Normal allocation. Ran out of reservation).

Mark-Compact (reduce) 31.4 (34.4) -> 31.4 (34.4) MB
  ... CppHeap allocation failure; GC in old space requested
```

两次崩溃的渲染进程运行时长分别为 **595416 ms（约 9 分 55 秒）** 与 **844512 ms（约 14 分 05 秒）**。

08:29 启动的那个实例，systemd scope 记账为：

```text
app-gnome-phrontis-18988.scope: ... 4.2G memory peak, 225.9M memory swap peak.
```

即进程组实际内存峰值约 **4.2 GB**，不是「JS 堆涨到 4 GB」——崩溃时 JS heap 只有 **31.4 MB**。

#### 3. 复现：长 agent 运行期间渲染进程 RSS 持续上涨

`/tmp/opencode/rss.log`，同一会话（第 1 章 段 2 · IBM-PC 的 I/O 地址空间与端口分配）打开 AI 教学并运行长 agent 任务时：

| 时间 | 渲染进程 RSS |
|---|---|
| 10:24:29 | 235144 kB |
| 10:25:59 | 245256 kB |
| 10:27:59 | 297564 kB |
| 10:29:00 | 428556 kB |
| 10:30:00 | 454572 kB |
| 10:32:30 | 528460 kB |
| 10:33:30（运行结束后） | 444484 kB |

同期页面状态：`思考中… 245.1s`、`查看前面 100/112 步`，即一次 **100+ 步、40+ 次工具调用**的长 agent 运行。

短对话不触发：当前实例在 10:34 重启后连续使用 20+ 分钟、只跑短回合，RSS 约 460–512 MB，未再崩溃。

#### 4. CDP 采样：DOM 节点和 JS heap 都不涨

`/tmp/opencode/mem.log`（15 秒一次采样，覆盖 10:04–10:40）：

- AI 教学页打开后：`Documents=2`、`Frames=1`、`Nodes≈2743`，之后长期维持在 2.7k–5.8k；
- `JSHeapUsedSize` 长期在 **29.6–34.6 MB**；
- `JSEventListeners` 在 315–3052 之间来回波动，没有单向累积；
- 同期（`/tmp/opencode/rss.log`）渲染进程 RSS 从 235 MB 涨到 528 MB。

结论：**这不是普通 JS heap 泄漏，也不是「活 DOM 节点数」泄漏**。但 `Nodes` / `JSHeapUsedSize` 不统计「已脱离文档但被原生对象拴住的 DOM」以及 raster / image / canvas 等原生缓冲，所以不能据此排除这些方向。

#### 5. 透明窗框是「崩溃后果」，不是「桌面故障」

- 主窗口：`transparent: true` + `frame: false`，见 `electron/main/index.ts:340-342`。
- `render-process-gone` 只打日志，不 reload、不显示错误页，见 `electron/main/index.ts:394-397`。
- Linux 点 X 会隐藏到托盘（`electron/main/index.ts:439-447`）；再点任务栏 / 托盘 / 应用图标时，`showMainWindow()`（`electron/main/index.ts:279-287`）或 `second-instance`（`electron/main/index.ts:1512-1518`）把**同一个已经没有渲染进程的窗口** `show()` 出来。
- 渲染进程死后没有内容可画，透明窗口就只剩圆角/阴影 —— 这就是「透明窗框」的全部来源。

#### 6. 排除 Linux 桌面 / 合成器

- OOM 发生在渲染进程自己的 Blink/Oilpan 堆里，退出码 133 是 V8 fatal；journal 没有 compositor / X11 报错。
- GNOME / X11 只决定「崩溃后长什么样」；同样的泄漏在 Windows 上也会崩，只是会看到一个空白/灰白窗口，而不是全透明。
- 桌面文件里的 `--no-sandbox` 是 `chrome-sandbox` 没有 setuid 的打包妥协，属于另一个安全问题，不是这次 OOM 的原因。

### 已确认的根因 / 诱因

**根因层级**：渲染进程的原生 Blink/Oilpan 内存被耗尽，V8 在 `CppHeap` 分配失败后主动 abort。

**已确认的诱因**：

1. **长时间 AI 教学 agent 运行**（100+ 步 / 40+ 次工具调用）是稳定相关项；
2. 用户报告的场景是「应用置于后台」；journal 在崩溃前多次出现 `[Window] evt blur`，但主进程没有记录 `hide()`，所以「后台」目前是用户场景，不是已证实的必要条件（窗口隐藏不会停掉主进程的 agent 循环，这一点成立）；
3. 短回合、纯工作台待机不会复现；取证时 `settings.json` 里 `themeFxEnabled=false`，主题粒子特效不是本次崩溃的因素。

**尚未定位**：

- 具体的原生分配点还不确定（没有 minidump：`/home/lousync/.config/knowbase/Crashpad` 只有 `client_id`，系统 core dump 也是关闭的）。
- 待验证方向（都未拍板）：
  - 流式期间每 60ms 对整段 Markdown 全量重解析（`src/components/shared/AssistantPanel/StreamBubble.tsx:81`、`:124-126`；`src/components/shared/MarkdownPreview.tsx:114-115`、`:243`）产生的**脱离文档 DOM / 原生文本对象**是否被 observer 或选区拴住；
  - raster / image / canvas 等原生缓冲是否在长回合中累积；
  - Electron 33 / Chromium 130 自身在该场景下的原生内存行为。
- 需要一次长运行的 heap profile（Chrome DevTools Memory / `chrome://memory-internals`）才能把范围缩到具体对象。

### 影响

- 渲染进程崩溃 → 当前 AI 教学回合丢失，界面无任何错误提示；
- 主进程留在托盘，点击图标只会把「透明死窗口」重新显示出来，用户会误以为应用卡死；
- 目前没有观察到数据损坏；退出托盘后重启即可恢复。

### 备注

- 本条原始记录只写现象与根因 / 诱因；**崩溃兜底已按 2026-11-02 拍板落码**，见下。
- 取证材料：`/home/lousync/.config/knowbase/crash-log.txt`、`/tmp/opencode/rss.log`、`/tmp/opencode/mem.log`、`/tmp/opencode/aiteach.png`。

### 修复记录（2026-11-02，仅崩溃兜底）

**已修：崩溃后的可见性与恢复路径**（`electron/main/index.ts`）

- `render-process-gone` 不再只打日志：
  - 首次崩溃（60 秒窗口外）→ 400ms 后 `webContents.reload()` 一次，把界面救回来；
  - 60 秒内再次崩溃 → **停止自动重载**（防崩溃循环），弹原生对话框：`重启界面` / `退出应用`；
  - `clean-exit` 不触发恢复。
- `showMainWindow()`（托盘 / 任务栏 / 二实例共用的唤起入口）先判 `webContents.isCrashed()`：崩溃态不再 `show()` 死窗口，改走恢复流程。
- `second-instance` 由复制的一套 `show/restore/focus` 改为直接调 `showMainWindow()`，避免两条入口再漂移。
- 崩溃日志留痕（`__kbLogRendererGone`）保留。

**未修：原生内存泄漏本身**

- 具体分配点仍未定位（无 minidump / core dump）；`StreamBubble` 全量重解析、raster / canvas 原生缓冲、Electron 33 原生行为三个方向都还需要一次长运行 heap profile。
- 兜底只保证「崩溃后不是透明死窗口」，不降低崩溃概率。

**取证基建（2026-11-02 晚）**：`electron/lib/rendererMemoryProbe.ts` + `rendererMemoryProbePure.ts`

- 主进程每 **30 秒**采一次主窗口渲染进程的原生内存，追加到 `userData/renderer-mem.log`
  （dev 为 `%APPDATA%/knowbase (dev)/renderer-mem.log`；1MB 轮转一代）。
  字段：`at pid rss peak jsHeap`，其中 `rss` / `peak` 来自 `app.getAppMetrics()` 的 `Tab` 进程
  —— 这正是 CDP 看不到的原生部分；`jsHeap` 只作对照。
- 崩溃时 `render-process-gone` 把**崩溃前最后一次样本**（`renderer-mem-last`）与
  **全进程 metrics 快照**（`app-metrics-at-crash`，含 peak）写进 `crash-log.txt`，
  下次复现可直接把「增长曲线 → 崩溃时刻」对齐。
- 需要逐个分配点定位时，用 `KNOWBASE_NATIVE_HEAP_PROFILE=1` 启动（等价于
  `--enable-heap-profiling=native`），再走 DevTools Memory → Native memory。
  默认关闭，避免改变运行形态与常驻开销。
- 采样只读 `app.getAppMetrics()` + `performance.memory`，**不主动 GC / 不 takeHeapSnapshot / 不 reload**。

**契约**：`.AGENT/scripts/desktop/verify-renderer-crash-guard.mjs`（12 项）+
`.AGENT/scripts/desktop/verify-renderer-memory-probe.mjs`（27 项，含真实纯函数断言）。

**下一步（需要真机长跑）**：复现一次 100+ 步的长 agent 回合，把 `renderer-mem.log` 的斜率与
`crash-log.txt` 的崩溃时刻对齐；若峰值只随时间线性上涨而与工具调用无关，再转向 Electron / Chromium
原生行为；若与 `StreamBubble` 流式重解析同步，则先做解析节流 / 脱离 DOM 回收。

## [x] F-2 工作台 AI 助手输入卡：`/` 无指令弹层；`/compress` 执行期间零反馈

> 来源：2026-10-29 用户实机反馈。本条已于 **2026-11-02 拍板**（方案 A / A / A）并当日落码，修复记录见本节末尾。

### 现象

1. 工作台 → 左栏书签「AI助手」→ 中央对话输入框键入 `/`，**没有任何指令弹层**；继续键入 `/compress` 回车，命令确实执行（结束后有结果 toast），但**执行期间界面无任何变化**。
2. 用户在压缩期间再输入一条以 `/` 开头的消息，右下角才出现「上一条指令 /compress 还在执行中，请等它完成」——这是整个压缩过程里**唯一**的进行中反馈。
3. 即使压缩成功，消息列表也不会变短：压缩只写纪要 + 推进检查点，原消息永不删除（`electron/lib/agentCompress.ts:47-95`）。

### 复现

1. AI 助手模块选一个已有若干轮消息的会话；
2. 输入框键入 `/` → 无弹层；
3. 键入 `/compress` 回车 → 无转圈 / 无占位 / 发送按钮仍可点；
4. 立刻再键入 `/compress` 回车 → 出现「上一条指令 /compress 还在执行中」。

### 证据

#### 1. 模块输入卡是手写副本，只接了「Enter 发送」

- `src/modules/ai-assistant/index.tsx:676-685`：裸 `textarea`；`onKeyDown`（`:681`）只判 Enter → `handleSend()`，没有 `/` 状态，也没有 import `SlashCommandMenu`。
- 弹层真源 `src/components/shared/SlashCommandMenu.tsx`，目前只有两个宿主接入：`src/components/shared/AssistantPanel/ChatBody.tsx:609`、`src/modules/ai-teaching/index.tsx:3294`。
- 「查询词派生 + 键盘语义」也各写一份：`ChatBody.tsx:277-303`、`ai-teaching/index.tsx:324` / `:1143-1169`；模块是第三处缺口。

#### 2. `/compress` 确实执行，但模块没有消费 `compressing`

- 发送链：`index.tsx:281-288 handleSend` → `runGuarded` → `execRun` → `useAiAssistant.ts:110` → `useAssistantChat.send` → `useAssistantChat.ts:815` 的 `handleChatCommand` 拦截。
- `useAssistantChat.ts:297` 有 `compressing` 状态（`onProgress` 设置），`:1100` 已导出给控制器。
- 兼容壳 `src/modules/ai-assistant/useAiAssistant.ts:68-121` **没有映射 `compressing`**，模块也没渲染占位；对照 `ChatBody.tsx:593-598`、`ai-teaching/index.tsx:3258-3263` 都有转圈行。

#### 3. 警告来自全局指令守卫，只挡「第二条 `/` 输入」

- `src/lib/chatCommands.ts:164-167` 的模块级 `running`。
- 若第二条是普通文字，`handleChatCommand` 在 `:141-142` 直接返回 false，消息会**真的并发发出**（比警告更糟）。

#### 4. 同链路缺口

| 缺口 | 位置 | 后果 |
|---|---|---|
| 发送按钮不判 `compressing` | `src/modules/ai-assistant/index.tsx:782` | 压缩期间仍可点发送 |
| Enter 不判输入法组合态 | `src/modules/ai-assistant/index.tsx:681` | 中文输入法选词回车误发 |
| `useAssistantChat.send` 不判 `compressing` | `src/components/shared/AssistantPanel/useAssistantChat.ts:795` | 任何宿主按 Enter 都能绕过禁用按钮并发发送 |
| 压缩完成后列表不变 | `electron/lib/agentCompress.ts:47-95` | 压缩只写 digest + 推进 `upto_id`，不删消息 |

### 根因

工作台 AI 助手模块 v3.11.0 统一到 `useAssistantChat` 时，只复用了**状态机**，输入卡仍是 v3.9.0 的手写子集。共享能力（斜杠弹层、压缩占位、IME 守卫）都长在 ChatBody / AI 教学各自的输入卡里，模块没有接；而 `compressing` 又没被兼容壳透出。新增宿主漏接共享能力时零报错，所以静默。

### 影响

- `/` 指令不可发现，用户只能靠记忆敲全名；
- 压缩数十秒无反馈，看起来像卡死；
- 压缩期间普通文字可并发发送（真正的问题），或收到误导性的「上一条指令…」警告；
- 中文输入法选词回车误发。

## [x] F-3 AI 教学工件栏页签过多：后面的被硬裁、够不到；⤢ 全屏按钮一起被挤出

> 来源：2026-11-02 用户截图反馈（AI 教学 → 中栏右侧工件分栏，已开 4 个 `.md` 工件页签，第 4 个在分栏右缘被拦腰裁掉）。记录阶段只登记问题与方案；当日下午按 P0 落码，见本节末尾。

### 现象

1. AI 教学模块中，右侧「工件」分栏（`ArtifactsPane`）打开多个文件页签后，页签条只显示前 3–4 个，**后面的直接被右缘裁掉**；
2. 页签条没有滚动条、没有渐隐或箭头提示，普通鼠标滚轮上下滚**不会横向滚动**；
3. 页签条右端的「⤢ 全屏阅读」按钮和页签在同一个滚动容器里，溢出时**一起被挤出可视区**，用户找不到全屏入口；
4. 触控板横向手势理论可滚，但鼠标用户没有别的够到手段。

### 复现

1. AI 教学 → 打开 4 个以上工件页签（讲义 / 练习 / 报告等 `.md` 都算），或把工件分栏拖窄；

4. 想切到被藏起来的页签 / 点 ⤢ → 够不到。

### 证据

#### 1. 页签条是「能滚但不告诉你能滚」

- `src/modules/ai-teaching/ArtifactsPane.tsx:89`：

  ```tsx
  <div className="shrink-0 flex items-center gap-0.5 px-2 pt-1.5 pb-0 overflow-x-auto [scrollbar-width:none] select-none">
  ```

  `overflow-x-auto` 说明内容确实可滚，但 `[scrollbar-width:none]` 把滚动条藏了；没有 `useStripScroll` 的滚轮接管、没有 `StripEdges` 渐隐、没有激活页签自动归位。

- 页签条目 `shrink-0 ... max-w-[170px] whitespace-nowrap`（`:90-104`）：只增不减，宽度上限 170px。
- 末尾 `flex-1 min-w-[8px]` 占位 + ⤢ 按钮（`:105-112`）**都在同一个滚动容器内**，溢出时随内容一起滚出视野。

#### 2. 分栏宽度天然容易触发

- `src/modules/ai-teaching/index.tsx:3313`：工件分栏 `defaultWidth={420} minWidth={280} maxWidth={780}`。
- 页签上限 170px ⇒ 默认 420px 下 **3 个页签就接近溢出**，4 个必溢出；拖到 280px 时 2 个就溢出。

#### 3. 同类问题在页面条已解决，工件栏没接

- 页面条（`WorkbenchPageBar` / `PageTabStrip`）在台账 F-16（2026-10-13）已经做过完整方案：`useStripScroll`（滚轮横滚 + 激活归位 + 边沿渐隐）+ `stripScrollPure.ts` 纯函数契约（`.AGENT/scripts/workbench-shell/verify-strip-overflow.mjs`）。
- 全仓用「`overflow-x-auto` + 隐藏滚动条」的页签条只有 `ArtifactsPane.tsx:89` 这一处 —— 属于同一类问题漏接，不是新机制。

### 根因

工件栏页签条只做了「允许滚动」，没做「**让人知道能滚、并且够得到**」：
- 滚动条被隐藏，且没有渐隐/箭头作为替代提示；
- 普通鼠标滚轮不会横滚（Chromium 只在 Shift+滚轮 / 触控板横向手势时横滚）；
- 没有激活页签自动滚入视野，切页签后可能仍停在看不见的位置；
- 固定动作（⤢ 全屏）与可滚内容混在同一个滚动容器，属于布局错误。

### 优化方案

#### P0（推荐先做：复用现成基建，改动最小）

1. **接入 `useStripScroll` / `StripEdges`**（`src/components/workbench/useStripScroll.tsx`）
   - 页签条外层加 `relative flex min-w-0 flex-1 items-center`；
   - 滚动容器挂 `ref={strip.setNode}`，保留 `overflow-x-auto [scrollbar-width:none]`；
   - 渲染 `<StripEdges edges={strip.edges} />`（渐隐底色 `--bg-secondary` 与工件栏一致）；
   - `useStripScroll(`${activeId ?? ''}|${tabs.length}`)`：激活变化 / 新增页签自动滚入视野；
   - 滚轮横滚由 hook 内置（无溢出 / Shift / 触控板横向手势时交回原生，不会吞页面滚动）。
2. **把 ⤢ 按钮移出滚动容器**

   - 删除 `flex-1 min-w-[8px]` 占位（按钮不再需要被内容推着走）；
   - 结果：无论页签多少，⤢ 始终固定在分栏右端。
3. **补激活属性**

- 行样式是 `cursor-pointer`（`:201` / `:262`），没有 `cursor-grab` 或把手提示。
- 另：`VaultTree` 行没有挂 `.kb-draggable`，但用户实测可拖 —— 当前 Chromium 下 `draggable` 属性仍生效；把手化时补 `.kb-draggable`，不要依赖这一版本行为。
- 项目内已有 pointer 阈值方案：`src/components/shared/ActivityBar.tsx:42` 的 `DRAG_THRESHOLD = 4` + `railDragGuard`（拖完挡一次 click）；但文件树仍用 HTML5 DnD，**浏览器启动阈值（约 4–5px）无法按业务调大**。
- 三处宿主都只是把 `onMove` 接到各自的 `workspaceRename`：`AiTeachFileTree.tsx:253`、`WorkbenchFileTree.tsx:232`、`knowledge/index.tsx:2433`。

### 根因

点击与拖拽共用同一个手势起点：整行既是 click target 又是 drag source。HTML5 DnD 的启动阈值由浏览器决定，无法按业务调大；也没有把拖拽收窄到明确的把手，或对拖后补发的 click 做抑制。于是「点一下」和「拖一下」在手指层面几乎无法区分。

### 方案

#### P0（推荐：把手化，改动小、三处同修）

- 把 `draggable` / `onDragStart` 从**整行**移到**行首图标**（文件 / 文件夹图标）：
  - 图标包一层 `<span draggable className="kb-draggable cursor-grab" title="拖动移动">`；
  - 行本身恢复纯点击（打开 / 展开），保留 `cursor-pointer`；
  - 点图标仍然冒泡到行（点图标 = 打开），只有从图标按下并拖动才移动；
  - 拖拽源补 `.kb-draggable`（铁律 9：body 的 `-webkit-user-drag: none` 继承链，HTML5 拖拽源必须显式恢复）。
- 只改 `VaultTree` 一处，AI 教学 / 工作台 / 笔记区三处同时生效。
- 备选：若图标 15px 太小、不好抓，在行尾加 `GripVertical` 把手（hover 才显形）；优先图标，避免新增一列。

#### P1（反馈与恢复）

- 拖动中给源行 `opacity-40`（当前 `VaultTree` 没有拖拽态视觉），让用户明确「正在拖」。
- 移动成功 toast 补「已移动 X → Y · Ctrl+Z 可撤回」（与 F-5 同批），让撤销可发现。
- 可选：按住 Alt 才允许整行拖动（给熟练用户保留整行手势），默认把手化。

#### P2（长期）

- 若要彻底消除 HTML5 DnD 的浏览器阈值问题，可改用 pointer events + 命中测试（同 ActivityBar / 日程拖拽），但树有大量 drop 目标，成本高；把手化已能解决绝大多数误触，暂不推荐重写。

### 验收

- 点击文件夹行的文字 / 空白 → 只展开 / 收起，不产生 `dragstart`；
- 从行首图标拖动 → 正常移动，目标目录高亮；

## [x] F-5 AI 教学资源管理器未接入文件操作撤销栈（Ctrl+Z 无效）

> 来源：2026-11-02 用户反馈 —— AI 教学区的资源管理器没有 Ctrl+Z 回溯。记录阶段只登记与分析；当日下午按 P0 + P1 落码，见本节末尾。

### 现象

1. 在 AI 教学左栏资源管理器里拖动 / 重命名 / 新建后按 Ctrl+Z，**没有任何反应**；
2. 同样的操作在工作台文件树、笔记区资源管理器里可以撤回（移动 / 重命名）；
3. 与 F-4 叠加时体感最差：误拖移动了文件，想 Ctrl+Z 撤回，结果撤不回。

### 证据

- `src/modules/ai-teaching/AiTeachFileTree.tsx` 全文**没有** `recordFileOp`：`onMove`（`:253-263`）、`commitRename`（`:166-176`）、`commitCreate`（`:150-163`）都直接调 `ws:*` IPC。
- `src/lib/fileOpHistory.ts:1-12` 明确覆盖「移动 / 重命名 / 新建」三类；`src/App.tsx:144` 全局安装 `installFileOpUndoShortcuts()`，Ctrl+Z 是「有栈才动作」。
- 对照：`src/components/workbench/WorkbenchFileTree.tsx:221` / `:241`、`src/modules/knowledge/index.tsx:1063` / `:1318` / `:1561` 都调 `recordFileOp({ kind: 'move', … })`。
- 附带发现：`kind: 'create'` 在全仓**没有任何调用方**（`grep recordFileOp` 只有 move）——所以「新建」在工作台 / 笔记区 / AI 教学三处其实都撤不回；`resources/help/键盘快捷键.md:25` 写的「重命名 / 删除 / 移动」也与实现不符（删除走系统回收站，按既有口径不纳入撤销栈）。

### 根因

AI 教学树只调 IPC，没有把成功的结构性操作写进共享撤销栈；全局 Ctrl+Z 依赖 `fileOpHistory` 的栈，空栈时静默不动。删除走系统回收站、程序内无 restore 通道，按既有口径不纳入撤销。

### 方案

#### P0（AI 教学接线）

- `onMove` 成功后：`recordFileOp` 记 move，`from = base + '/' + src`、`to = base + '/' + dstDir + '/' + name`（先判 `r.ok`，当前代码未判就刷新）。
- `commitRename` 成功后：同样记 move，`from = base + '/' + relPath`、`to = base + '/' + parent + '/' + name`。
- `commitCreate` 成功后：记 `{ kind: 'create', rootId, relPath: 实际 relPath, isDir, name }`（用 IPC 返回的 `relPath`，主进程重名会自动加后缀）。
- `doDuplicate` 成功后：记 create（副本也是新建），可选。
- 路径口径：`fileOpHistory` 用**仓库相对路径**；AI 教学树内部是产物根相对路径，记录时拼 `base`。

#### P1（刷新与提示）

- 撤销 / 重做后的树刷新：优先复用现有 `onWsFsChanged`（fsWatcher）→ `setTreeRefreshSeq`；若要确定性，补 `kb-fs-op-changed` 监听（`FileOpResult.dirs` 已给受影响目录）。
- 移动 / 重命名成功 toast 补「Ctrl+Z 可撤回」，让撤销可发现。

#### P2（全局口径）

- 把 `kind: 'create'` 记录补到工作台文件树与笔记区（`fileOpHistory` 已支持，缺调用方）；
- 修正 `resources/help/键盘快捷键.md` 的撤销覆盖描述（删除不在栈内）。

### 验收

- AI 教学里拖动一个文件 → Ctrl+Z 移回原目录，树即时刷新；
- 重命名 → Ctrl+Z 改回；
- 新建文件 / 文件夹 → Ctrl+Z 移除（走回收站）；
- 删除 → 不进撤销栈，回收站可找回；
- 焦点在聊天输入框时 Ctrl+Z 仍是文本撤销（`isEditingInput` 让路）；
- 契约：静态断言 `AiTeachFileTree` 含 `recordFileOp` 且 move 路径带 `base`；`fileOpHistory` 的 move / create 纯函数用例不回归。

## [-] F-1 关闭「AI 助手思考模式」后回答仍像在思考 + 单轮输入 token ≈3.8k 偏高？

> **★ 搁置（2026-10-05）**：开发负责人判「问题不大」，本条整体移入 DP `Phrontis/搁置功能与想法/AI思考模式真关闭/README.md`（定性、token 基线与方向 A/B/C 全文随迁）。复活从那边起，此处存档不再推进。

**提出（2026-09-29，开发负责人原话）**：「我在 AI 助手那里将思考模式关闭后，我问他问题他回答我看起来还是在思考的样子（可能在我这个用户看来是在思考），然后输入的 token 是 3.8k 这个量高不高，因为我知道现在的 AI 助手内置的提示词很多（我询问它的问题是：你现在能做什么工作）」。

**现象**：① 关闭思考模式后，回答过程仍表现为「在思考」；② 该轮**输入 ≈3.8k tokens**。

### ★ 初步定位（未拍板、未动码）

**「思考模式」与「显示思考过程」是两个独立开关，语义没被区分**：

| 开关 | 真源 | 实际作用 |
|---|---|---|
| `assistantThinking`（AI 助手思考模式） | `src/lib/settings.ts:240` | `useAssistantChat.ts:187` 读出 `thinking` → `agentChat(..., thinking ? 'medium' : 'off')`（`:344`）；主进程只在**模型具备推理能力**时才透传 `reasoning_effort`（`electron/lib/llmService.ts:326-328`，能力由 `REASONING_MODEL_RE` 名字启发式判定） |
| `aiShowThinking`（显示思考过程） | `src/lib/settings.ts:233` | 决定推理链是否在**折叠区显示** |

⇒ **关掉「思考模式」只是「不主动加强深度」**（不传 `reasoning_effort`），**不等于模型不思考**。若所用模型**本身就是推理型**（`REASONING_MODEL_RE` 命中：`reasoner` / `r1` / `qwq` / `qwen3` / `o1-` / `thinking` …），关掉该开关后它照样吐 `reasoning_content`，界面照样显示思考链 ⇒ 用户看到的「还在思考」。

**倾向结论**：**大概率不是 bug，而是两个开关的语义没被区分**（用户以为「关思考模式」= 不再思考，实际只是不额外加深度）。**但也可能**是 UI 侧的「思考中」状态提示与真实事件不匹配（真的没在推理、只是转圈文案不当）。

### ★ 定性（2026-09-29，开发负责人补充模型与时长后）

**开发负责人补充**：用的是**千问 3.x flash**；该轮**思考时长约 6 秒**。

- 模型名含 `qwen3` ⇒ **命中 `REASONING_MODEL_RE`**（`electron/lib/llmService.ts:308`），被判为「具备思考能力」。
- 关掉思考模式只是**不发 `reasoning_effort`** —— `buildOpenAiBody` 的守卫是 `if (req.effort && req.effort !== 'off' && REASONING_MODEL_RE.test(req.model))`（`electron/lib/llmService.ts:326-328`），`off` 直接跳过。
- **Qwen3 是混合推理模型，自身就会产思考链**；而全仓 **grep 不到任何 `enable_thinking` / `chat_template_kwargs` / `no_think` 通路** ⇒ **本应用目前没有「真的让它别想」的手段**。
- 「思考约 6 秒」= 它**确实思考了**，不是 UI 假象。

**⇒ 定性：不是 bug，是「能力缺口 + 语义落差」。** 设置项 `assistantThinking` 的 desc 写的是「不透传思考参数」（技术表述准确），但用户会读成「关掉就不思考了」。**走哪个处置方向待开发负责人拍板。**

**处置方向（候选，勿自行决定）**：

- **A · 补能力（唯一真正省时间省 token 的）**：为 Qwen3 这类混合推理模型接 `enable_thinking:false`（或 `/no_think` 软开关）通路，让「关闭」名副其实；并让「显示思考过程」随之一致。
- **B · 改文案**：明确写「不加强深度 ≠ 模型不思考」，并在所用模型是思考型时给出提示。
- **C · 只改显示（治标）**：关掉思考模式时折叠区不显示思考链 —— 模型仍思考、仍费 token，只改观感。

### token 3.8k 是否偏高 —— **不高**，且比应用自身的基线还低

- **输入 = 常驻系统提示词 + 常驻 core 工具 schema + 会话历史**。对「你现在能做什么工作」这类**极短问题**，几乎全是**固定开销**，不是用户内容带来的。
- **★ 实跑基线（2026-09-29 重跑，命令 `node .AGENT/scripts/ai-tools-audit/measure-tool-schema.mjs`）**：**core 14 个工具的 schema 合计 ≈ 24,958 字符 ≈ 7,873 tok / 轮**；ondemand 21 个另计 ≈13,174 tok（**默认不注入**）。脚本会覆写 `out-schema-baseline.txt`（已刷新；顺带修正了一处陈旧数值：`knowledge.graph-topology` 4269→4346 字符）。
  - 附注：`AGENTS.md` 铁律 16 写「core 13 个」，脚本实测 **14** —— 铁律那个数字偏旧，宜回头校正（不属本条）。
- **⇒ 有一个对不上的数**：若 14 个 core 工具**全发**，光工具就 ~7.9k，总输入**不可能只有 3.8k**。二者不能同时成立 ⇒ 说明该轮**实际发出的工具少于 core 全量**。最可能的成因：`buildToolsPayload`（`electron/lib/agentService.ts:365-405`）按**模块权限** `checkModulePermission`，把「无权模块」的工具**整个剔出模型视野** —— 开发负责人若没给 quiz / checkin / pomodoro / knowledge 等模块授权，payload 会明显缩小（只剩 `vault.*`(4) + `tool.request` + `help.search` + `web.*`(2) ≈ 4k 量级，与 3.8k 量级吻合）。
- **结论**：3.8k **不算高**，属正常范围（甚至偏保守）；真正值得盯的是**权限全开时的 ~8k 工具固定开销**。若要精确归因（提示词 / 工具 / 历史各占多少），需一次「空会话首轮」实测拆数 —— **本条只登记，不落码。**

**处置方向**：见上方「★ 定性」的三条候选（**A 补能力 / B 改文案 / C 只改显示**），待拍板。

## [x] F-2 AI 助手「助手定制」菜单被边缘 / 主体截断 + 建议按钮上移

**提出（2026-09-29，开发负责人原话）**：「AI 助手的助手定制按钮点击后的菜单会被各种边缘截断，而且当 AI 助手扩大后点击左侧边栏的助手定制按钮后，菜单会被中间的主体部分截断，而且我觉得将这个按钮放在最上面跟返回顶部按钮放在一起比较合适」。

**现象**：点「助手定制」（`AssistantEntryButton`）弹出的条目菜单，在多种宿主下被**裁切 / 截断**：
1. **一般场景**：菜单被面板边缘「各种截断」；
2. **AI 助手扩大（整页 aiChat 标签）后**：点**左侧边栏**里的助手定制按钮，菜单被**中间主体部分**截断。

### ★ 根因（已定位到代码，非猜测）

菜单是**纯 `absolute` 定位、无翻折 / 无夹取 / 无 portal**：`src/components/shared/AssistantPanel/AssistantEntry.tsx:60`

```
className="kb-pop absolute left-0 top-full z-30 mt-1 w-60 rounded-lg border ..."
```

- `left-0` + 固定宽 `w-60`（240px）⇒ 菜单**一律向右**铺开。宿主面板一窄、按钮又靠右时，菜单右半必然越过面板/中栏边界，被父容器的 `overflow-hidden` 裁掉 —— 这正是「扩大后左栏按钮的菜单被中间主体截断」的成因（`AiChatSidebar` 的定制按钮在双 Tab 行的**最右端**，`:144`）。
- 项目里**已有**两套成熟定位 hook 专治此事：`src/lib/useAnchoredMenu.ts`（锚点元素 + 放不下翻折 + 双向 clamp，现有 4 处模块在用）与 `src/lib/useContextMenuPosition.ts`（吃点击坐标）。本菜单**两个都没用**，是裸 `absolute`。
- 三处宿主共用同一按钮：`AssistantPanel/index.tsx:454`（悬浮侧栏头部）、`AssistantPanel/ChatBody.tsx:277`（右栏 AI 态轻头部）、`AssistantPanel/AiChatSidebar.tsx:144`（aiChat 标签左栏会话侧栏）。

**处置方向（待拍板）**：改用 `useAnchoredMenu`（锚点翻折 + clamp），必要时菜单 portal 到 body —— 与 beta 台账 `F-1` 的右键菜单同族修法。

### 位置建议（开发负责人提出，2026-09-29 已确认指向）

> 「将这个按钮放在最上面跟返回顶部按钮放在一起比较合适」

**「返回顶部按钮」= 左栏顶部的 🏠「返回总览」**（已向开发负责人确认）。故形态 = 把 `AssistantEntryButton` 从 `AiChatSidebar` 的双 Tab 行（`src/components/shared/AssistantPanel/AiChatSidebar.tsx:144`）**移到左栏模块态头部那一行**，与 🏠 / 🔒 并列。

**该行现状**（`src/components/workbench/WorkbenchLeftPanel.tsx:302-317`，模块态头部）：🏠 返回总览 · 🔒/🔓 锁定 · **`modActionsRef` 模块动作槽**（源码注释明写「模块自己的按钮 portal 到这里，与二钮同组居中」）。

**★ 实现上已有现成通道，不必新造**：`modActionsEl` 这套 portal 机制早就在用 —— 博客（`src/modules/blog/index.tsx:330`）与知识库（`src/modules/knowledge/index.tsx:1996`）都把各自的头部按钮 portal 进它。**aiChat 只是没接线**：`src/App.tsx:1320` 的 `case 'aiChat'` 只传了 `sidebarEl`（→ `wbModSlotEl`），**缺 `modActionsEl`** ⇒ 要动 = 给 `AiChatTab` 加该 prop，让 `AssistantEntryButton` 改 portal 进 `modActionsEl`。

**范围待确认**：`AssistantEntryButton` 共三处宿主 —— aiChat 整页左栏（`AiChatSidebar.tsx:144`，**本次要动的**）、悬浮侧栏头部（`AssistantPanel/index.tsx:454`）、右栏 AI 态轻头部（`AssistantPanel/ChatBody.tsx:277`）。后两处的头部行**没有 🏠、也没有 `modActionsEl` 可用** ⇒ **是否一并调整待拍板**（本条描述的场景是「扩大后」，故默认只动 aiChat 那处）。

**附带收益**：按钮落到左栏头部**最左端**后，菜单自最左向右铺开 240px 基本不出界 —— 与上面的截断修法（`useAnchoredMenu` 翻折 + clamp）叠加，两处问题一并缓解。

> **已落码（2026-10-01）**：按上「范围」只动 aiChat 那处 —— `AiChatTab`（`ChatBody.tsx`）新增 `modActionsEl` prop 并透传给 `AiChatSidebar`；`AssistantEntryButton` 从双 Tab 行撤下，`createPortal` 到左栏模块态头部 `wbModActionsEl`；`App.tsx` `case 'aiChat'` 补传 `modActionsEl`。后两处宿主（悬浮侧栏头部 / 右栏 AI 态轻头部）**未动**（其头部无 🏠/`modActionsEl`）。

## [x] F-3 分享卡片「题目区」里的数学公式未在框内居中

**修复方向（待拍板）**：① `knowledge.create-page` 的 `exec.data` 若含 `path`/`relPath` 则纳入 `vaultPath` 提取（同 `visual.html` 待遇），凑不出路径的（schedule/checkin 等纯结构化写）维持不入「文件」审计但可考虑入「条目」级审计（op 列结构化动作）；② 或放宽 `recordSessionFileChange` 允许 `file` 为空的条目，右栏卡对无 `file` 条目禁点击（点击直达只对有 `file` 的开放）。

**验证**：让 AI 新建知识页 → 右栏改动文件卡出现该条目且可点击打开；待办/打卡类动作按拍板口径呈现；既有 vault.write 路径条目不回归。

## [ ] F-13 文件树改名 / 拖拽移动「分类目录」不级联 categories.json 登记（归类失效 + 脏条目）（2026-10-05）

**来源**：2026-10-05 开发负责人对话 ——「现在笔记区中的【新建目录】和【新建分类目录】有啥问题，我新建了一个目录然后想让 AI 助手往里面写页面失败了，说只能写在分类目录中」。排查「两种目录的区别」时定位到本条；「AI 只能写分类目录」那一半是 `builtin.knowledge.create-page` 的 categoryName 只查登记表（`electron/lib/builtinTools.ts:833`，既有设计），**本条是与 AI 无关的登记级联缺口**。

**现象**：对「新建分类目录」建的目录（= categories.json 有登记的顶层分类）在**文件树**里改名或拖拽移动后：
1. 该分类下页面**归类失效** —— 页面 categoryId 由索引重建时按「父目录路径精确匹配登记 path」推导，磁盘路径变了、登记没跟着变 ⇒ 页面全部掉「未分类」；
2. 文件树**删除分流失配** —— path→catId 匹配不上 ⇒ 再删除走普通回收站通道，categories.json 留下指向已不存在目录的脏条目（删除分流注释里明写要避免的事）；
3. 连带 `builtin.knowledge.create-page` 的 categoryName 也查不到该分类。

**定位 / 根因（已读码）**：
- 文件树改名 `handleTreeRename`（`src/modules/knowledge/index.tsx:1059`）与拖拽移动 `handleTreeMove`（`:901`；VaultTree 目录行可拖，`src/components/shared/VaultTree.tsx:251` `draggable`）共用 `workspaceRename` → 主进程 `renameWorkspacePath`（`electron/lib/workspaceManager.ts:662`）：纯 fs 改名 + 失效索引，**不碰 categories.json**；
- 级联只存在于分类树侧的 `updateKnowledgeCategory` → `vaultRenameCategory`（`electron/lib/kbStore/knowledgeVaultRepo.ts:547`，磁盘改名 + 字典 name/path 及子孙 path 级联）；
- 归类推导 `resolveCategoryIdByPath`（`electron/lib/kbStore/knowledgeIndex.ts:491`）与删除分流 `handleTreeDelete`（`src/modules/knowledge/index.tsx:1013`）都依赖 path 命中；**删除已按登记分流**（`:1007-1049`），改名 / 移动没有做同样的分流 —— 不对称即坑源。

**处置方向（待拍板）**：
1. 渲染层修法：文件树 rename / move 提交处按删除同款 `path → catId` 检测，命中登记条目改走 `vaultRenameCategory`；
2. 或下沉主进程：`renameWorkspacePath` 检测 categories.json path 命中后统一级联（两处渲染入口都免改）；
3. **移动场景另有一层设计矛盾**：「分类恒根层」是拍板过的设计（`index.tsx:915` 注释），拖成子目录本身就冲突 —— 可考虑直接禁掉分类目录的拖拽移动（只留改名）；且 `vaultRenameCategory` 只有原地改名语义，放开移动需新增「移动 + path 级联」函数。

**涉及模块 / 文件**：`src/modules/knowledge/index.tsx`（handleTreeRename / handleTreeMove / handleTreeDelete 分流参照）· `src/components/shared/VaultTree.tsx`（目录行拖拽）· `electron/lib/workspaceManager.ts`（renameWorkspacePath）· `electron/lib/kbStore/knowledgeVaultRepo.ts`（vaultRenameCategory）· `electron/lib/kbStore/knowledgeIndex.ts`（resolveCategoryIdByPath）。

**与既有能力的关系**：与本台账 F-11 同属「AI 写知识库」链路的邻接问题（F-11 是写审计漏记，本条是登记级联），无重叠、可各自独立修。

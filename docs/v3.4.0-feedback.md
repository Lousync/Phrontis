# v3.4.0 体验反馈台账

> **用途**：v3.4.0 是窗口骨架大改版（三栏外壳 + 书架六格式 + 书市）。改版必然带来「以前能做的、现在做不了」与「以前顺手、现在别扭」的落差。本文件是**这轮体验反馈的唯一归集处** —— 开发负责人逐条报问题，这里记现象、定位、根因、处置方向，攒够一批再统一开修。
>
> **与其他文档的分界**：
> - 与 `docs/pending-fixes.md`（B-n）：那份是**通用**待修 bug 台账，滚动了 B-1…B-26。本文件只收 **v3.4.0 改版引发的落差**，是本轮的专项台账。**若某条确认是通用 bug（与改版无关），转登记进 `pending-fixes.md` 并从本表移除**。
> - 与 `CHANGELOG.md`：那份面向用户、只写已交付的功能。本文件是**开发侧**的待办输入。
> - 与 DP `Phrontis/更新计划/v3.5.0.md`：跨版本的排期项在那；本文件只管 v3.4.0 自身的修补。
>
> **编号**：`F-n`（Feedback），全局递增不复用。状态标记 `[ ]` 待办 / `[~]` 处理中 / `[x]` 已修 / `[-]` 不修（有意设计，保留说明）。
>
> **本文档收两类，分两个区段，前缀不同，勿混**：
> - **`F-n`（缺陷 / 落差）** —— 「以前能、现在不能」（改版落差）或「本来就不对」（bug）。**本区段**。
> - **`N-n`（New，功能需求）** —— 「从来没有、现在想要」（新增能力）。见文末 **「功能需求」区段**。二者各自维护状态总览表。
>
> **★ 关键前提：先判「是不是有意设计」。** v3.4.0 有一批能力是**按方案主动移除**的（如图标条拖拽排序，见 F-1）。这类先标 `[-]` 并给出方案依据，**等开发负责人拍板「确实要恢复」再转 `[ ]`** —— 避免把设计决策当 bug 修回去。

## [ ] F-1 图标条不能拖拽移动图标位置、不能右键唤出隐藏菜单

**报障（2026-09-23，开发负责人原话）**：「现在的左侧 tab 栏不能拖动移动图标的位置和排序了，而且不能右键唤出菜单来进行图标的隐藏了」。

**现象**：图标条（最左窄列）的按钮位置固定，无法拖动换位；右键点击无菜单，无法隐藏某个图标。

**性质判定：这是 v3.4.0 的**有意设计**（非回归），但**开发负责人已拍板恢复**。**

**依据（代码注释白纸黑字）**：`src/components/shared/ActivityBar.tsx:13-14`

> **固定按钮**：AI 教学 / 回收站 / 插件市场 / 动态 / 设置——**不再提供拖拽排序与右键显隐**（旧 `activityBarOrder` / `activityBarHidden` 设置键随之废弃，见方案 §3.5）；

**旁证**：
- 按钮清单是硬编码常量 `RAIL_BUTTONS`（`ActivityBar.tsx:31`），非从 settings 读取。
- 旧设置键 `activityBarOrder` 仍留在 `src/lib/settings.ts:170`，但 `ActivityBar` 已不消费它（仅 `appModules.ts` 注释提到）。属**残留键**，可考虑清理或保留兼容。
- **方案原文已核对**（`Phrontis/方案与调研/workbench-shell-design.md`，DP 库；主仓无副本）：§3.4 第 77 行明写 **「图标条不再提供拖拽排序/显隐菜单（v15 定稿固定 5 项），旧 `activityBarOrder` / `activityBarHidden` 设置键废弃」**；§3.5 第 89 行把两键列入「废弃键」清单。**结论 = 原型 v15 定稿时的有意决策，非回归。**

**★ 一处需要澄清的能力转移**：同方案 §3.3 第 71 行，`{ hidden: string[], order: string[] }` 这套**显隐 + 排序**能力在 v3.4.0 里**给了左栏书签**（`workbenchLayout.bookmarksHidden` 等），图标条没有。也就是说「用户可自定义入口的顺序与显隐」这件事在新外壳里换了个载体 —— 从图标条搬到了左栏书签。**若开发负责人真正想要的是「能自定义图标条」，那与「用左栏书签自定义」是两种产品取向，需先明确要哪个。**

### ★ 处置决定：**D 选项 —— 拖拽排序 + 右键显隐，两者都恢复**（2026-09-23 开发负责人拍板）

**已核实的三项有利条件**（实现成本比预想低）：

1. **旧实现完整存在于 git 历史** —— 提交 **`89156e5c`**「活动栏拖拽排序 + 右键切换模块可见性 + 侧栏拖拽关闭」（2026-06-21）：`ActivityBar.tsx` +188 行，用的是 **HTML5 拖拽重排**，顺序持久化到 `activityBarOrder`；右键空白处弹菜单勾选显隐。**可整段参照取回**，不必从零设计。
2. **两个设置键都还在、无人消费** —— `src/lib/settings.ts:170-171` 的 `activityBarOrder` / `activityBarHidden` 仍在（`type: 'json'`，`ui: false`）。**恢复不需要新增键**；方案 §3.5 把它们列进「废弃键」清单是当时判断，现按 D 选项**撤回该废弃决定**。
3. **右键菜单有现成基建可复用** —— `src/lib/useAnchoredMenu.ts`（v3.4.0 为右栏 `⋯` 菜单新抽的 hook：实测 `offsetHeight` 定位 + 边界翻转 + 外部点击/Esc 关闭）。**不要重写菜单定位**。

**实现要点**：

- **数据源**：`RAIL_BUTTONS` 由硬编码常量改为「可排序集合 + 消费 `activityBarOrder` / `activityBarHidden`」；顺序归一化可复用 `src/lib/appModules.ts:117` 的「活动栏归一化顺序（含被隐藏的项）」。
- **拖拽**（铁律 9）：图标条在 `-webkit-user-drag: none` 的继承链上，**拖拽源必须挂 `.kb-draggable`**（定义在 `src/styles/index.css:171`）。旧实现用的是 HTML5 拖拽 —— 图标条是**窄列纵向排序**，需确认 HTML5 拖放在此场景可靠（若出现静默失败，按铁律 9 换 pointer events，参考日程拖拽的 `dragGuard` 250ms 兜底）。
- **动效**（铁律 13）：排序过程走既有令牌，**不另造过渡**；拖拽跟手不加动画。
- **右键菜单**：复用 `useAnchoredMenu`，菜单项 = 各模块勾选（`activityBarHidden`）。注意旧实现的口径「用户 / 设置不受影响」（这两个不被隐藏）。
- **契约**：`.AGENT/scripts/verify-workbench-shell.mjs` 有「图标条按钮集断言」（方案 §3.4 第 180 行提到）—— 改成动态集合后**该断言需同步改写**，否则会锁住旧的固定清单。
- **待确认的一个设计问题**：图标条与**左栏书签**若都能自定义顺序/显隐，两处是否需要一致性（书签已有 `workbenchLayout.bookmarksHidden`）。**倾向各自独立**（图标条 = 应用级模块入口，书签 = 工作台内导航），但需在实现时明确，避免用户困惑「为什么有两套隐藏」。

## [ ] F-3 托盘图标有时变成紫色方块

**报障（2026-09-23，开发负责人原话）**：「软件在左下角的后台的这个图标有时候显示正常有时候显示不正常」，附截图 = 一个**紫色方块**。

**根因：已定位。紫色方块就是代码里的兜底占位图 —— 托盘图标加载失败时才会出现。**

**证据链**：

1. **兜底图确认为紫色方块**：`electron/main/index.ts:224-227`，三个候选路径全失败时执行 `nativeImage.createFromDataURL('<内置 base64>')`，并 `console.warn('[Tray] All icon candidates failed to load -> using builtin placeholder')`。**我把这段 base64 解码成 PNG 渲染出来验证过，就是一个紫色方块 —— 与截图完全一致。**
2. **三个候选路径中，只有第一条在 dev 下可能成功**（`electron/main/index.ts:216-220`）：
   - ① `app.getAppPath()/build/icon.png` ← **唯一有效候选**
   - ② `process.resourcesPath/build/icon.png` ← dev 下 = `node_modules/electron/dist/resources/build/icon.png`，**实测不存在**
   - ③ `process.resourcesPath/icon.png` ← 同上，**实测不存在**
3. **所以问题必然出在候选 ①** —— 即 `app.getAppPath()` 的取值时机/结果变化。

**★ 「有时正常有时不正常」的原因 —— 已确证的部分与尚未确证的部分**

**已确证**：

- **紫色方块 = 兜底图**（见上，已解码验证）。
- **候选 ② ③ 在 dev 下恒失败**（实测路径不存在）→ **只有候选 ① 有效**。
- **不是「某个 worktree 缺图标」**：两仓 `build/icon.png` 均存在且 **md5 相同**（`83a370352475baddb1f80a68557f198b`）。
- **不是启动时序问题**：`createTray()` 位于 `app.whenReady().then()` 回调内（`index.ts:696` 起，`createTray()` 在 1065 行），**不是 ready 之前调用**。此前的时序假设已排除。

**尚未确证（需实机抓日志）**：候选 ① 为何会时成时败。目前**未能在本会话复现**（Electron 探针在本沙箱起不来，已尝试三种启动方式均无输出；`tmp/` 下亦无历史日志可查 —— 已于本轮清理）。

**给下次复现时的快速判据（一击定位，不必再推理）**：

> **dev 窗口里按 F12 打开 DevTools 看不到主进程日志，要看启动终端**。托盘失败时主进程会打印：
> ```
> [Tray] All icon candidates failed to load -> using builtin placeholder
> ```
> **见到这行 = 确证走了兜底**，接下来只需打印 `app.getAppPath()` 与 `process.cwd()` 的实际值即可定位。

**修复方向（按两种可能分岔，待判据确认后二选一）**：

- **若是路径问题**（最可能）→ 把 `createTray` 的候选路径改为不依赖 `getAppPath()` 的推导方式（如以 `__dirname` 为基准，或按 `app.isPackaged` 分支：打包走 `process.resourcesPath`、dev 走 `app.getAppPath()`），并保证 dev 下 `build/` 的相对位置稳定。
- **若是时序 / 竞态问题** → 把 `createTray()` 移到更晚（如首个窗口 `ready-to-show` 之后），或改为对图标路径的**延迟求值 + 重试**。

**附注（必须一起改）**：任务栏按钮图标用的是**同一路径**（`index.ts:272` 的 `icon: join(app.getAppPath(), 'build', 'icon.png')`，注释已写明「dev 下 electron.exe 无内置图标 → 白板按钮的根因」）。**修 F-3 时两处要同批改**，否则会出现「托盘修好了、任务栏还是白的」。

**另有一条低成本加固（与根因无关，但值得做）**：既然兜底图是个无意义的紫方块，**不如把它换成真正的应用图标**（哪怕是小尺寸 PNG 的 base64 内联），这样即使将来再走兜底，用户看到的也是正常图标而非怪异的紫方块 —— 至少不会误以为「图标坏了」。

## [x] F-4 更新说明点「知道了」开出空白 editor 标签页

**已修（2026-09-23）**。根因是**三处缺陷叠加**，三处同批修掉：

1. **`dismissReleaseNotes` 绕开了归一化函数**（`App.tsx:458`）—— 它原先写 `(s.startupTab as TabName) || 'blog'`，直接用**未迁移的原始设置值**。而同一文件 `App.tsx:425` 的启动路径**正确调用了** `resolveStartupTab(s.startupTab, s.activityBarHidden)`。**同一份数据、两条路径、一条归一化一条不归一化** —— 这是空白页的最近原因。
   - 修：改用 `resolveStartupTab(s.startupTab, s.activityBarHidden)`。该函数已含「不可启动 / 已隐藏 / 已退役 ⇒ 落 knowledge」的钝规则，`editor` 不在 `STARTABLE_MODULE_IDS` 里，自然被兜住。
2. **手动入口不记来源**（`App.tsx:693`）—— `tabBeforeNotes` 原先只在**自动弹出**路径（`:448`）赋值，手动打开时恒为 `null`，于是必定走「回落启动项」这条分支。
   - 修：手动入口同样写 `tabBeforeNotes.current`（与自动路径同口径，`releaseNotes` 自身除外）。
3. **`openTab` 无有效性守卫**（`App.tsx:315`）—— 实现只有 `setActiveTab(tab)`，任何脏 TabName 都会直达渲染层，`switch` 无对应 case 即空白。
   - 修：`setActiveTab(isTabName(tab) ? tab : resolveStartupTab(undefined, s.activityBarHidden))`。**这是根治** —— 命令面板 / 设置 / 插件命令 / 深链 / 旧持久化值都走 `openTab`，此后一律不会再产生空白页。

**验证**：`tsc --web` 0 错；`verify-startup-tab.mjs` **53 项全绿**；`verify-workbench-shell.mjs` **139 项全绿**。

**遗留的同类风险（未修，建议后续排查）**：缺陷 1 的形态是「**同一个设置值有两条消费路径，一条归一化、一条没有**」。这类「归一化函数有、但某个调用点绕开它」的问题可能不止这一处 —— 建议全仓 grep `as TabName` 的**强制断言**，逐个确认是否该改走 `isTabName` / `resolveStartupTab`。（本次修前 `App.tsx` 里只有 `:461` 一处此类断言，已清。）

**原始根因分析（保留作过程记录）**

**缺陷 1 —— `dismissReleaseNotes` 不关当前页，而是另开一个**（`src/App.tsx:458-462`）：

```js
const dismissReleaseNotes = useCallback(() => {
  const prev = tabBeforeNotes.current
  tabBeforeNotes.current = null
  openTab(prev ?? ((s.startupTab as TabName) || 'blog'))
}, [openTab, s.startupTab])
```

它调 `openTab(prev)` —— **只切 activeTab，从不关闭 `releaseNotes` 标签**。

**缺陷 2 —— `tabBeforeNotes` 只在「自动弹出」路径被赋值**（`App.tsx:448`），手动打开更新说明时不赋值：

```js
tabBeforeNotes.current = prev === 'releaseNotes' ? null : prev   // 仅在 shouldAutoOpen 的定时器里
```

故**手动打开**时 `tabBeforeNotes.current === null` → 回落到 `s.startupTab || 'blog'`。

**缺陷 3（空白页的直接原因）—— `startupTab` 中存着已退役的 `'editor'`，且 `openTab` 不做校验**：

- `editor` 模块在 v3.4.0 **已整体退役、从 `APP_MODULES` 移除**（能力并入笔记区；`grep "'editor'" src/lib/appModules.ts` 零命中）。
- 但 `startupTab` 是**全局持久化设置**（`src/lib/settings.ts:178`，`scope: 'global'`），**用户旧设置里存的 `'editor'` 不会被自动迁移**。
- `openTab` 实现极简（`App.tsx:315`），**没有任何有效性校验**：

```js
const openTab = useCallback((tab: TabName) => {
  setActiveTab(tab); setSidebarOpen(true); setPalette(null)
}, [])
```

→ `activeTab = 'editor'`，渲染层 `switch(activeTab)` 无对应 case → 返回空 → **空白页**。

**为何标签页标题显示 `editor`**：标签标题取自 `TabName` 字符串本身（模块 label 查表失败时回落为 id）。

**关联**：缺陷 3 的「退役模块 id 残留在持久化设置里」是**一类问题**，不止 `startupTab` —— 建议顺手全仓排查其他可能出现旧 TabName 的持久化点（如 `workbenchLayout` 相关键、`openTabs` 的持久化若有）。

### 缺陷 2 —— 「无需登录」与「需要凭据」是两个不同维度的信息，被并排渲染成矛盾　★ **已修（2026-09-23，彻底改法）**

**位置**：`src/modules/bookmarket/SourcesView.tsx:80-87`

```jsx
{s.authType ? (
  <span ...>{s.hasCredential ? '凭据已存' : '需要凭据'}</span>   // ← 静态标签：由 authType 决定
) : (
  <span className={tagCls}>无需登录</span>
)}
```

而**同一行右侧**还有一枚**连通性状态**（`CONN_META`，`shared.ts:44`）：

```js
'need-credential': { dot: 'var(--warning)', label: '需要凭据' },
```

这枚来自**实测探测结果**（`sourceClient.ts:149`）：

```js
if (status === 401 || status === 403) return 'need-credential'
```

⇒ **左边「无需登录」= 配置声明（`authType == null`），右边「需要凭据」= 实际探测到 401/403**。两者语义不同、维度不同（声明 vs 实测），但 UI 把它们摆在**同一行**、且**用了同一个词「需要凭据」**，于是看起来自相矛盾。

**为什么古登堡中文源会探测出 401/403**：这不是配置错误，而是**该端点真实的行为**。Gutenberg 的部分检索端点在特定查询下（或对中文检索、无 UA、频率限制时）会返回 401/403，`sourceClient` 据此判 `need-credential`。**它其实不是「要凭据」，是「被拒了」** —— 但这两种情况被合并成了同一个状态值。

### 修复方向（两处独立，可分开做）

**修缺陷 1（低风险，建议先做）**：
- `builtin.booksource.draft` 的 `authType` enum 补 `'none'`，并在 description 里写明**「公版 / 公共目录源请显式传 none，或直接省略该字段」**。让「不需要认证」有**可表达的取值**，模型就不会猜。
- 同类检查：`bookSourceEnum` 的默认参数是 `'none'`，说明执行体本就支持 —— 只是 schema 没暴露。

**★ 修缺陷 2 —— 采用「彻底改法」：`SourceConnectivity` 由三态拆为四态**（2026-09-23 开发负责人拍板）

**新状态设计**（拍板口径：401 与 403 语义不同，拆开）：

## [~] F-7 沉浸阅读状态下页面不能向下滚动

**报障（2026-09-23，开发负责人原话）**：「页面在沉浸式阅读状态下，页面不能向下滑动了」。

**★ 结论：根因已定位到「滚动根被变换劫持」，但复刻探针未能在 Chromium 里复现 —— 此项**须在实机确认一次再动手**，不可仅凭代码推理就改。**

**已确证的架构事实**（读码 + 真机 devbridge 量测，非推理）：

1. **沉浸阅读的滚动容器是 `src/modules/knowledge/index.tsx:1784`** 的 `<div className="h-full overflow-y-auto">`。
2. **该容器的祖先链上没有 `overflow:hidden` 把它逼成滚动根**——`ImportZone`（`:1754`）是 `relative h-full`，无 overflow。所以「内层不滚、外层裁剪」这一经典病灶在本分支**不成立**。
3. **孤立复刻探针：滚动正常**。用 Chromium（`tmp/probe-scroll-fillboth.mjs`）搭同构 4 层链（`.kb-view-fade` 动画 → `h-full overflow-hidden` → `h-full overflow-y-auto` → 3000px 内容），`outer` 即便带 `animation: … both`（计算 `transform` 仍为 `none`），`inner.scrollTop` 也能正常到 500。**⇒ 「`animation-fill-mode: both` 制造 containing block 劫持滚动根」这一候选**已证伪**（case ① 复刻通过；仅 case ④「inner 去掉 overflow-y:auto」失败，符合预期）。**

**⇒ 因此故障**不在**这条静态布局链上，而在「运行期该分支被换掉 / 高度约束断裂」这一类**（铁律 11 的 `h-full` vs `flex-1` 同族病）。**下次实机必查的三处**：

- **入口在跑吗**：进沉浸阅读后，量 `document.querySelector('div.h-full.overflow-y-auto')` 的 `clientHeight` 与 `scrollHeight`。若 `clientHeight === scrollHeight` ⇒ 容器没拿到高度（高度约束断了，内容高度没超过容器）；若 `clientHeight` 正常但 `scrollTop` 推不动 ⇒ 被祖先变换/paint 容器劫持。
- **谁是滚动根**：`document.scrollingElement`，以及沿祖先链逐个量 `overflow` / `transform` / `filter` / `will-change` / `contain`——任一非 `none` 的 `transform` 都会把 `position:fixed` 的包含块从视口改到该元素（本模块顶部「退出阅读」悬停区是 `absolute`，不受影响；但若别处有 `fixed` 就会错位）。
- **是不是高度约束**：查从 `App.tsx` 的那句 `min-h-0`（`:1445`，注释已写明这是**同类病的历史修复**）到模块根，是否有一条链漏了 `min-h-0` / `h-full`。**铁律 11 与 `docs/release-notes-design.md` §4 是同一类病**：`min-height:auto` 让 flex item 被内容撑破 → 外层 `overflow-hidden` 裁掉 → 「看得见上半屏、滚轮不动」。

**一处顺带发现（与本 bug 未必相关，但同属该函数）**：`readingPage` 是 `enterReading` 时的一次性快照（`:551-566`），仅由 `openInReading`（`:573`）/`openPageInReader`（`:599`）刷新，**阅读期间不随正文变化重取**。故「边读边被外部（AI 工具 / 另一窗口）改了该页」时，沉浸阅读显示的是旧正文——`MarkdownPreview` 拿的是 `readingPage.contentMd`（`:1820`）。**这不是「不能滚动」的原因**（旧内容一样可滚），但同属该函数的行为缺陷，修 F-7 时顺手确认是否需要「阅读态正文跟随刷新」。

**探针留档**：`tmp/probe-scroll-fillboth.mjs`（playwright-core + `%LOCALAPPDATA%\ms-playwright\chromium-1234`）——**否定证据**，勿删，修此 bug 时先跑它确认结论仍成立。

## [~] F-9 PDF 左侧目录跳转与目标页不匹配

**报障（2026-09-23，开发负责人原话）**：「我打开一本 pdf，他左侧的目录跳转跟实际的跳转页面不匹配」。

**★ 根因已确证：目录 dest 的页号是 **0 基**，却被当成 **1 基**页码使用 —— 整体差一页。**

**代码链**：

1. `src/components/shared/pdf/PdfOutlineTree.tsx:16-25` `destToPageNum`：解析 dest 数组首元素 `{num,gen}` 并 `return d[0].num`。
2. `PdfRailPanel.tsx:133-137` `jumpOutline`：`const p = await destToPageNum(...)`，随后 **`if (p >= 1) goto(p)`**。
3. `goto`（`:128-131`）派发 `KB_PDF_GOTO_PAGE` → `PdfReaderView.tsx:1194` `goPage(d.page)` → `:816` `Math.max(1, Math.min(Math.round(num), total))` → `:817` `scrollPageIntoView({ pageNumber: target })`。

**判据（pdf.js 官方 typing，`node_modules/pdfjs-dist/types/src/display/api.d.ts:823-827`）**：

> `getPageIndex(ref: RefProxy): Promise<number>` — "A promise that is resolved with the page index, **starting from zero**, that is associated with the reference."

dest 数组首元素**就是** `RefProxy`，故 `.num` 是 **0 基页索引**。而下游 `goPage` 全程按 **1 基**（`Math.max(1, ...)`、`pageNumber`）——**契约在最上游这一处就错了**。

**两个用户可见症状（都对应得上「不匹配」）**：

- **差一页**：绝大多数条目跳到**上一页**。
- **点了没反应**：dest 指向第 1 页（`num: 0`）时 `p === 0`，**过不了 `if (p >= 1)` 守卫 → 静默无跳转**（无 toast、无报错）。

**修复方向**：`destToPageNum` 改为**返回 1 基**。正确写法不是 `+1` 了事，而是走 pdf.js 的**权威换算**：

```ts
// 首元素是 RefProxy ⇒ 用 getPageIndex 拿 0 基索引再 +1。
// ★ 不要退回「按 .num + 1」：.num 是 PDF 对象号（obj num），
//   对页号不连续 / 有非页对象的 PDF 会算错；getPageIndex 才是「这份文档里它是第几页」的唯一真相源。
const idx = await pdf.getPageIndex(ref)   // 0 基
return idx + 1
```

**须同批处理的连带项**：

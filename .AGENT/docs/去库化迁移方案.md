# 去库化迁移方案：弃用 SQLite，全面改读仓库

> 目标（用户 2026-09-02 拍板）：正式版用户升级后，把旧数据导入仓库；最终**删除 SQLite 全部内容、彻底弃用 sql.js**。
> 本文把「怎么做」和「为什么不能立刻删」讲清楚，并给出可执行的分期路线。
>
> **演进（2026-11-14）**：本方案已全部落地——sql.js 已随 R6 移除、双读源开关 `storageKnowledge` 已下线、kbStore 实现层已外迁独立包 `phrontis-core`（主仓经 `phrontis-core/kbStore/*` 导入）。下文分期与「现状基线（2026-09-02 实测）」均为历史快照，现状口径以 AGENTS.md 为准。

---

## 一、结论先行

**方向认同，但执行顺序必须调整。**

用户原话的顺序是「导出 → 删 SQLite → 弃用」，这个顺序会**必丢数据**。正确顺序是：

```
先把模块的读源切到仓库  →  验证稳定  →  再删 SQLite
       （修新桥）                        （拆旧桥）
```

原因一句话：**导出只是复制数据成文件，并不改变应用从哪读。**
在任何一个模块能读仓库文件之前删掉 SQLite，那个模块就永久读不到数据了。

## 三、如果现在就删 SQLite，会发生什么

以知识库为例，当前调用链：

```
渲染层 → ipcRenderer.invoke('kb:getPages') → knowledgeRepo → getDatabase().prepare('SELECT ...')
                                                                    ↑
                                                              数据在这里
```

删掉 SQLite 后，`getDatabase()` 返回空库，26 个知识库 handler 全部返回空数组。
用户看到的就是**知识库空白**——而数据其实还在仓库的 .md 文件里，只是没人去读。

其他 18 个 repo 同理。所以删除动作必须排在**所有模块改造完成之后**，也就是本文的 P4。

## 五、P0 详解：知识库改读仓库

### 5.1 存储格式（已由迁移器定稿，见 `scripts/migrate-to-vault.mjs`）

```
<Vault>/<空间>/<笔记本>/<文件夹>/<页面>.md
<Vault>/_inbox/<页面>.md                    category_id 为空的零散页
<Vault>/_attachments/<owner_type>/<owner_id>/<文件名>
<Vault>/.knowbase/modules/knowledge/{categories,pages,tags,page-tags,pack-imports}.json
```

frontmatter（严格对齐 `electron/lib/kbStore/mdStore.ts`，保证可回读）：

```yaml
---
id: 906ec46a-005a-4c13-8863-b10a9d8bc657
title: 数据结构基本概念
category: 546df50e-9dea-44b0-ac9c-7ce830bc5270
tags: [数据结构, 绪论]
starred: true
sortOrder: 0
created: 2026-08-26T15:56:18.282Z
updated: 2026-08-29T07:43:04.319Z
attachments: [_attachments/knowledge_page/<id>/xx.pdf]
---
```

### 5.2 必建的中间层：metadataCache

知识库模块要按分类树、标签、收藏、排序查询——这些不能每次都全盘扫 .md。
需要一层内存索引（对标 Obsidian 的 metadataCache）：

- 启动时扫仓库内所有 `.md`，解析 frontmatter，建 `id → {path, title, tags, category, starred, updated}`
- 文件变更时增量更新（本期可先全量重建，P5+ 再上 watcher）
- 落盘缓存到 `.knowbase/cache/knowledge-index.json`，二次启动秒开

**这是 P0 的前置任务，没有它，知识库列表页会卡死。**

### 5.3 knowledgeRepo 改造清单

26 个 handler 逐个改读 metadataCache + mdStore，重点：

- `kb:getPages` / `kb:getCategories`：读索引，不读库
- `kb:savePage`：写 `.md` 文件（mdStore 原子写）+ 更新索引
- `kb:deletePage` → 走回收站（现有 `trash` 包），不能直接删文件
- `kb:movePage` / `kb:renameCategory`：改 .md 路径 + 重写引用它的正文链接
- 附件读写改走 `workspaceManager` 的授权根模型（已有 `resolveSafe`，勿重复实现）

### 5.4 迁移器产品化

把 `scripts/migrate-to-vault.mjs` 的核心逻辑抽成 `electron/lib/vaultMigration.ts`，
改用 `getDatabase()`（sql.js）而非 `node:sqlite`，暴露：

- `vault:legacySummary` → 旧数据摘要（页数/博客数/附件数/总字节）
- `vault:importLegacy` → 执行导入，返回报告
- `vault:importProgress` → 事件推送进度（沿用 `knowledgePack:progress` 的模式）

UI 挂载点：
- `WelcomeOverlay`：检测到旧数据 → 显示「检测到旧版本数据（216 篇知识、36 篇博客、491 MB）」+ 导入入口
- 设置面板：常驻「导入旧数据到当前仓库」手动入口

### 5.5 双读源开关与回滚

设置里加 `storage.knowledge: 'sqlite' | 'vault'`（默认 sqlite）。
用户导入后手动切换；出问题切回 sqlite 立刻恢复。
**在 P0 灰度验证通过前，不要把这个开关的默认改成 vault。**

## 六、数据安全底线（正式版用户）

1. **导入前自动备份**：`knowledge.db` → `knowledge.db.pre-vault.bak`（只改名，零拷贝）
2. **非破坏性**：导入全程只读源库，绝不删改
3. **可重跑**：默认跳过已存在文件，`--overwrite` 才覆盖
4. **可回滚**：双读源开关 + 原库保留
5. **禁止提前删库**：只有 P5 全部分期验证完毕后，才允许移除 SQLite

## 七、附件策略（用户已选：智能）

- 导入前先算总大小
- **< 200 MB**：直接复制，不打扰用户
- **≥ 200 MB**：弹窗让用户选「全部复制 / 仅内容不复制附件」
- 不复制时，frontmatter 的 `attachments` 仍记录原始路径，并标注为「外部引用」

## 八、待决事项

1. **P0 是否要包含 quizRepo（错题本 24 handler）？** 它属于知识库生态，Plugin API v2 设计里也把它列为 `kb.store.*` 的首个验证对象。建议单独立项，不塞进 P0。
2. **双链 `[[文件名]]` 什么时候做？** 路线图阶段 1 里有，但会显著改变知识库的数据模型。建议 P0 只做单读源切换，双链放 P0 之后。
3. **P5 之后插件生态怎么办？** `contributes.tables`（插件自建 SQL 表）与去库化正面对冲，需 `kb.store.*` 提供等价能力后再下线。
4. **灰度策略**：先内测版切 vault、正式版保持 sqlite 多久？

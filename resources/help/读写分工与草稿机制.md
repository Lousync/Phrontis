# 核心概念：读写分工与草稿机制

**一句话**：正文**只能在中间区的编辑页签里写**，侧栏（左栏、知识库侧栏）只负责浏览与文件管理；而知识库只收录带 `id` 的文件，其余的算草稿。

这一页解释了新用户最容易撞墙的两件事，读完能省下大量困惑。

## 一、读写分工

| | 中间区编辑页签 | 侧栏（左栏文件树 / 知识库侧栏） |
|---|---|---|
| 职责 | **写正文**：编辑内容、续写、加标签 | **管文件**：新建、重命名、移动、删除、浏览 |
| 操作对象 | 磁盘上的 `.md` 文件（仓库里的真实文件） | 同一批文件，以目录树呈现 |
| 能不能写正文 | 能（唯一入口） | **不能**（有意设计，不是缺失） |

侧栏可以**新建文件 / 文件夹 / 知识页**（右键菜单或头部「＋」），建完点开就在中间区的编辑页签里写内容。所以：**「新建」在侧栏里找得到，但「写正文」只在中间区**——两者不是一回事。

## 二、草稿机制：什么样的文件才算「知识库页面」

知识库只收录**带 frontmatter `id` 的 .md 文件**。没有 `id` 的文件被当作**草稿**：

- 草稿只在编辑区可见，知识库一律不显示；
- 草稿不算「丢了」，文件实实在在躺在仓库里；
- 草稿变成页面只需补三行：

```yaml
---
id: my-first-note
title: 我的第一篇笔记
---
```

`id` 全库唯一、**一旦确定不要再改**（改名会导致双链与反向链接失配）。`title` 只是显示名，随便改。

> **为什么这么设计？** 让你可以随便写、随便存 —— 临时记的片段、没写完的半成品不会把知识库塞满。只有当你明确「这篇要进知识库」时才正式收录。

## 三、自查三步：写了文件但知识库看不到

1. 打开那个文件，看开头有没有 `---` 包裹的 frontmatter 区块；
2. 确认区块里有 `id:` 这一行，且值不为空；
3. 保存后回知识库，正常会立刻出现（写盘后会广播刷新）。

还是看不到，再看是不是**落在被忽略的目录里**（仓库根的 `.ignore` 规则，gitignore 语法）。

## 常见误用

- 只在正文写了标题、没加 frontmatter → 属于草稿，符合预期；
- 字段名写成 `ID` / `Id` → 不识别，**字段名区分大小写**；
- `id` 留空或写了空格 → 视为无效，仍算草稿；
- 把 `id` 改成中文或带斜杠的路径 → 虽然能存但容易在双链解析时出问题，建议用英文 + 连字符；
- 以为「知识库看不到 = 文件丢了」，于是重新写一遍 → 结果仓库里出现两份；
- 用系统资源管理器直接改了文件，但软件里的列表没刷新 → 写盘后会广播刷新，通常 1 秒内自动跟上；迟迟不动再切一下模块（索引按需重建）。
